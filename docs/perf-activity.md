# 활동 로그 성능 측정

활동 화면(`widgets/activity/ActivityView.tsx`)의 이벤트 로그를 많이 펼쳤을 때 얼마나 느린지 재고, 목록 가상화를 적용한 기록.
이슈 #109 · 브랜치 `perf/activity-virtual` · 결정은 [adr/0021](./adr/0021-활동-로그-가상화.md).

## 한눈에

이벤트 3,000건을 전부 펼친 상태, 프로덕션 프로파일링 빌드, 5회 중앙값.

| | 변경 전 | 변경 후 |
| --- | --- | --- |
| 처음 그리기 (화면 재진입) — React 커밋 시간 합 | 680.5ms | 3.1ms |
| 새 이벤트 1건 도착 — React 커밋 시간 합 | 773.8ms | 3.1ms |
| 스크롤 중 프레임 간격 (중앙값 / p95) | 16.7 / 17.0ms | 17.2 / 21.6ms |
| DOM 노드 수 (화면 전체) | 21,158 | 347 |
| JS heap (GC 뒤) | 21.2MB | 9.5MB |

- **가상화 혼자 낸 수치가 아니다.** 고친 것은 셋이고 몫이 다르다 (아래 "무엇이 얼마나 줄였나"). 가상화 없이 나머지 둘만 고쳐도 처음 그리기는 140.1ms, 새 이벤트는 38.9ms까지 내려간다
- **스크롤은 나아지지 않았다.** 변경 전에는 스크롤이 React를 거치지 않아 비용이 0이었다. 가상화하면 스크롤할 때마다 줄을 갈아 끼워야 한다 — 처음 적용했을 때는 프레임 간격이 53.8ms까지 나빠졌고, 원인 둘을 고쳐 변경 전 수준으로 되돌린 값이 위 표다
- **3,000건은 "더 보기"를 100번 누른 상태다.** 화면에 처음 들어오면 30건만 받는다 (`limit=30`). 평소 쓰임에서 체감할 차이는 아니다

## 측정 방법

### 환경

| | |
| --- | --- |
| 기기 | Intel Core i7-1165G7 (4코어 8스레드) · RAM 16GB · Windows 11 |
| 브라우저 | **헤드리스** Chrome 157 (`--headless=new`), 창 1440×900, CPU 스로틀 없음 |
| 런타임 | Node 22.14 · Next.js 16.3.5 (Turbopack) · React 19.2 |
| 빌드 | `next build --profile` + `next start` (React 프로파일링 빌드) |

룸 피드 측정([perf-room-feed.md](./perf-room-feed.md))은 보이는 Chrome 창에서 했지만 이번에는 헤드리스로 했다. 보이는 창이 다른 창에 가려지면 Chrome이 `requestAnimationFrame`을 초당 1회로 줄여 스크롤 값을 쓸 수 없었다. 전후를 같은 방식으로 쟀으므로 비교는 유효하지만, 헤드리스의 프레임 값은 GPU가 붙은 실제 화면과 절대값이 다를 수 있다.

### 더미 데이터

실제 BE 대신 목 서버 `perf/mock-server.mjs`를 쓴다 (룸 피드 측정 때 만든 것에 이벤트 경로를 더했다). 값은 전부 지어낸 것이다.

- `GET /projects/:id/events` — 30건씩, `before` 커서. 실제 API와 같은 모양
- 이벤트 3,000건, 시드 고정 난수. 구성은 **가정**이다: 태스크 수령 30% · 제출 25% · 검증 완료 25% · 태스크 생성 12% · 룸 메시지 8%
- 이름을 찾는 목록은 태스크 20개 · 멤버 2명 · 에이전트 0개. 실제 프로젝트는 태스크가 더 많고, 줄마다 태스크 이름을 찾는 비용(`tasks.find`)이 그만큼 더 든다

### 무엇을 쟀나

`PerfProfiler`가 활동 화면을 React `<Profiler>`로 감싼다 (`NEXT_PUBLIC_PERF=1`일 때만). 시나리오는 `perf/collect.js`의 `perfActivity.run`.

| 상황 | 재현 방법 | 값 |
| --- | --- | --- |
| 처음 그리기 | 3,000건을 다 펼친 뒤 받은 편지함으로 갔다가 활동으로 돌아온다 | 그 사이 커밋의 `actualDuration` **합** |
| 새 이벤트 1건 | 목 서버가 이벤트를 더하고 `events` 신호를 보낸다 → 다시 읽기 → 다시 그리기 | 위와 같음 |
| 스크롤 | 맨 위에서 맨 아래까지 600프레임에 걸쳐 프레임마다 약 184px씩 내린다 (초당 약 11,000px — 빠르게 휙 내리는 속도) | `requestAnimationFrame` 간격, Long Task, 그동안의 커밋 |
| 크기 | 3,000건을 펼친 직후 | `document.getElementsByTagName("*").length`, CDP `Performance.getMetrics`의 heap (GC 뒤) |

- 상황마다 예열 3회(스크롤은 1회)를 버리고 5회를 잰다
- 커밋 시간은 **합**으로 적는다. 가상화한 목록은 처음 그리기가 커밋 5개로 나뉘어 가장 큰 커밋 하나로는 비교가 되지 않는다
- 커밋 시간에는 레이아웃 · 페인트가 들어 있지 않다. 그쪽은 "누른 뒤 목록이 보일 때까지"로 본다: 1,272ms → 46ms

### 다시 재는 법

```bash
node perf/mock-server.mjs                                   # http://localhost:3900
NEXT_PUBLIC_PERF=1 NEXT_PUBLIC_API_BASE_URL=http://localhost:3900/api pnpm exec next build --profile
pnpm exec next start -p 3001
node perf/run-activity.mjs prod-3000-이름                    # 헤드리스 Chrome으로 끝까지 돌린다. 약 6분
```

결과는 `perf/results/prod-3000-<이름>-activity.json`. Chrome 경로가 다르면 `CHROME=...`으로 넘긴다.

## 무엇이 얼마나 줄였나

같은 절차로 여섯 번 쟀다. 단위 ms, 중앙값.

| 결과 파일 (`prod-3000-…`) | 코드 | 처음 그리기 | 새 이벤트 | 스크롤 프레임 중앙값 / p95 | 33ms 넘는 프레임 (600개 중) | 스크롤 중 커밋 시간 합 |
| --- | --- | --- | --- | --- | --- | --- |
| `baseline` | 변경 전 | 680.5 | 773.8 | 16.7 / 17.0 | 0 | 0 |
| `virtual` | ① 가상화만 | 15.6 | 22.4 | 53.8 / 83.2 | 592 | 18,402 |
| `virtual-fmt` | ① + ② 날짜 포매터 재사용 | 4.6 | 9.2 | 27.9 / 41.9 | 150 | 6,084 |
| `virtual-memo` | ① + ② + 줄 `memo` · `getItemKey` 고정 | 4.5 | 8.8 | 26.9 / 40.7 | 131 | 5,596 |
| `virtual-select` | ① + ② + `memo` + ③ `select` 고정 — **최종** | 3.1 | 3.1 | 17.2 / 21.6 | 0 | 624 |
| `virtual-plain` | 최종에서 줄 `memo` · `getItemKey` 고정만 뺌 | 4.4 | 2.8 | 18.1 / 24.3 | 0 | 1,694 |
| `novirtual-fixed` | 가상화 없이 ② + ③만 | 140.1 | 38.9 | 16.7 / 17.0 | 0 | 0 |

### ① 목록 가상화

`@tanstack/react-virtual`의 `useVirtualizer`. 화면에 걸린 줄(+위아래 8줄)만 그리고, 나머지는 `<ol>`의 위아래 padding으로 자리만 잡는다. 3,000건이어도 그려지는 줄은 27~41개다.

- DOM 노드 21,158 → 347, heap 21.2MB → 9.5MB는 가상화의 몫이다 (`novirtual-fixed`는 21,158 · 21.3MB 그대로)
- 처음 그리기 140.1 → 3.1ms, 새 이벤트 38.9 → 3.1ms도 가상화의 몫이다 (`novirtual-fixed` → 최종)
- 대신 스크롤이 React를 거치게 됐다. 프레임마다 커밋이 4번 일어난다 — 아래 ② ③이 없으면 한 프레임에 30ms가 든다

### ② 날짜 포매터 재사용 (`shared/lib/format.ts`)

줄 하나가 `toLocaleTimeString` · `toLocaleDateString`을 3번 불렀다. 이 함수들은 부를 때마다 포매터(`Intl.DateTimeFormat`)를 새로 만든다. Node에서 따로 재면 3,000줄에 765ms, 포매터를 한 번 만들어 재사용하면 32ms다 — **변경 전 렌더 시간의 대부분이 이것이었다.**

- 가상화 없이도 처음 그리기 680.5 → 140.1ms (`novirtual-fixed`, ③ 포함)
- 가상화한 뒤에는 스크롤 프레임 53.8 → 27.9ms
- `fmtTime` · `fmtDate`는 룸 피드 등 다른 화면도 쓴다. 그 화면들도 같이 빨라졌을 것이지만 **재지 않았다**
- 문자열이 그대로인지는 `format.test.ts`가 확인한다

### ③ `select` 함수를 훅 밖으로 (`entities/event/api/eventApi.ts`)

`useProjectEvents`의 `select`가 인라인 함수였다. TanStack Query는 함수가 바뀌면 `select`를 다시 돌리므로, 렌더마다 100페이지를 합쳐 3,000건 배열을 만들고 이전 결과와 깊은 비교를 했다. 변경 전에는 렌더가 드물어 드러나지 않았고, 가상화로 스크롤 중 커밋이 프레임당 4번이 되자 프레임을 잡아먹었다.

- 스크롤 프레임 26.9 → 17.2ms, 33ms 넘는 프레임 131 → 0개
- 780건만 펼쳤을 때는 이 문제가 보이지 않았다 (17.8ms). 건수에 비례하는 비용이라 3,000건에서만 드러났다

### 줄 `memo` · `getItemKey` 고정

넣었을 때(`virtual-fmt` → `virtual-memo`)는 차이가 없었다 — ③에 가려져 있었다. ③을 고친 뒤 빼 보니(`virtual-plain`) 스크롤 중 커밋 시간 합이 624 → 1,694ms, 프레임 p95가 21.6 → 24.3ms로 나빠져서 남겼다. 둘을 따로 떼어 재지는 않았다.

## 측정하면서 알게 된 것

- **가상화가 병목의 원인을 고친 것이 아니었다.** 변경 전 680ms의 대부분은 DOM이 아니라 날짜 포매터였다. 가상화만 넣으면 그리는 줄 수가 줄어 처음 그리기는 좋아지지만, 같은 비용이 스크롤로 옮겨 가 더 눈에 띄는 곳에서 드러난다
- **뒤로가기에서 목록이 비는 버그.** 스크롤 요소를 `ref`로 넘겼더니, 캐시가 있어 첫 렌더부터 목록을 그리는 경우(재진입)에 자식의 layout effect가 부모의 ref보다 먼저 돌아 가상화가 스크롤 요소를 영영 잡지 못했다. 첫 진입은 로딩 상태를 한 번 거쳐서 드러나지 않았다. 스크롤 요소를 state로 넘겨 고쳤다
- **보이는 창에서는 스크롤을 잴 수 없었다.** 창이 가려지면 `visibilityState`는 `visible`인데 프레임만 초당 1회로 준다

## 바꾸지 않은 것

- **새 이벤트가 올 때 받아 둔 페이지를 전부 다시 읽는 것.** 3,000건이면 요청 100개가 차례로 나간다. 신호를 받은 뒤 새 이벤트가 보일 때까지 1,343ms → 415ms로 줄었지만, 남은 415ms는 거의 이 요청들이다. 이벤트는 지워지지 않는 기록이라 첫 페이지만 다시 읽어 앞에 붙이는 방법이 있지만 이번 범위가 아니다 (`eventApi.ts`의 `ponytail:` 주석)
- 대시보드의 최근 활동 (같은 `EventRow`를 쓰지만 첫 페이지 일부만 보인다)
- 룸 피드 가상화 (→ [perf-room-feed.md](./perf-room-feed.md) "바꾸지 않은 것")
