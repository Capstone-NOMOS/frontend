# 에이전트의 질문은 누구에게 가야 하는가

> 코딩 에이전트가 작업 중에 사람에게 묻는 질문(Claude Code의 AskUserQuestion)을, 여러 사람이 함께 개발하는 팀에서 그 결정을 내릴 권한이 있는 사람에게 바로 보내는 문제를 다룬다. 실제 질문 데이터, 사용자 커뮤니티의 논의, 공개 연구, 그리고 우리가 직접 돌린 라우터 비교 실험을 바탕으로 이 방향이 의미가 있는지, 기술적으로 되는지, 무엇은 새롭지 않은지를 정리했다.

## 한눈에 보기

<!-- stats -->

- 60% | 실제 팀 질문 173개 중 1순위로 대표(PM)가 정할 질문
- 13% | 지금 NOMOS 서버 기본 규칙(반대 역할)이 맞힌 비율
- 94% | LLM이 owner를 직접 고를 때 정확도(sonnet, 실제 질문)
- 104초 | 사람이 질문에 답하기까지 걸린 시간 중앙값(p90 약 31분)

<!-- /stats -->

1. **Claude Code의 질문 채널은 구조적으로 한 사람에게만 간다.** 서브에이전트는 질문 도구를 쓸 수 없고, 실험 기능인 agent teams도 팀원의 권한 요청을 리드 세션 한 곳으로 올린다. 여러 사람이 각자 에이전트를 돌리는 팀에서 "이 질문은 백엔드 담당이 정할 일"이라는 개념 자체가 없다.
2. **질문의 다수는 프론트와 백엔드 사이가 아니라 대표(PM) 소관이다.** 실제 팀 세션에서 나온 질문 173개를 라벨링해 보니 1순위 owner가 PM인 질문이 60%, 자기 소관이 35%, 상대 기술 역할 소관은 6%였다. 지금 서버의 기본 라우터는 PM을 고를 수 없어서 13%만 맞혔다.
3. **owner 배정 자체는 어렵지 않다.** LLM이 직접 고르면 실제 질문 94%, 백엔드 팀이 정답을 붙인 20문항 95%를 맞혔다. 키워드 규칙은 익숙한 데이터에서는 78%였지만 처음 보는 도메인에서는 53%로 떨어졌다.
4. **진짜 어려운 부분은 정확도가 아니라 대표에게 몰리는 부하와 답을 기다리는 시간이다.** 가장 정확한 라우터도 질문의 73%를 대표에게 보냈다. 기획안에 있던 "확신이 낮으면 대표에게"라는 단계는 오히려 첫 수신자 정확도를 떨어뜨렸다.
5. **그래서 이번 학기 목표는 "3역할 팀에서 할당이 맞게 되는가"와 "공통 계약 위에서 병렬 개발이 되는가" 두 가지로 좁힌다.** 역할을 더 쪼개거나 비판, ERD, 스케줄러 에이전트를 붙이는 일은 뒤로 미룬다. 교수님 피드백과 같은 결론이다.

> 이 문서의 숫자에는 출처를 붙였다. 기획 단계 표에 있던 "일반 에이전트 42%, NOMOS 91%" 같은 값은 예시값이라 쓰지 않았다. 실제 질문 라벨은 Claude가 붙인 임시 정답이고 사람 검수 전이다. 같은 계열 모델 라우터에 유리할 수 있다.

## 1. 문제: 질문은 한 줄로만 흐른다

AskUserQuestion은 Claude Code가 작업 중에 사람에게 선택지를 주고 묻는 도구다. 질문 1~4개, 선택지 2~4개를 한 번에 보내고, 사람이 고른 답을 받아 같은 작업을 이어 간다([Agent SDK 문서](https://code.claude.com/docs/en/agent-sdk/user-input)).

혼자 쓸 때는 이 구조가 자연스럽다. 질문을 받는 사람이 곧 결정권자이기 때문이다. 문제는 여러 사람이 각자 에이전트를 돌리는 팀이다. 프론트엔드 개발자의 에이전트가 "정원이 찬 스터디에 신청하면 서버가 어떤 에러 코드를 주나요?"라고 물으면, 그 질문은 프론트엔드 개발자 화면에 뜬다. 답할 권한도 정보도 없는 사람이 메신저로 백엔드 개발자를 찾아가 묻고, 답을 받아 다시 입력한다.

Claude Code 공식 문서로 확인한 구조는 이렇다.

| 사실 | 출처 |
| --- | --- |
| 서브에이전트에서는 AskUserQuestion을 쓸 수 없다. 질문은 메인 세션을 운영하는 사람에게만 간다 | [Agent SDK 사용자 입력](https://code.claude.com/docs/en/agent-sdk/user-input) |
| agent teams(실험 기능)에서 팀원의 권한 요청은 리드 세션으로 올라가고, 팀 전체가 한 사람의 한 세션 안에 있다. 팀은 세션마다 하나이고 세션끼리 공유할 수 없다 | [agent teams 문서](https://code.claude.com/docs/en/agent-teams) |
| 같은 문서가 "프론트엔드, 백엔드, 테스트를 각각 다른 팀원이 맡는 계층 간 조율"을 대표 사용 예로 든다. 역할을 나눈 병렬 개발 자체는 이미 제품 기능이다 | 같은 문서 |
| 질문에 시간 제한(`askUserQuestionTimeout`)을 걸면, 시간이 지나 Claude가 스스로 판단해 진행하고 나중에 다시 물을 수 있다 | [도구 레퍼런스](https://code.claude.com/docs/en/tools-reference) |
| Agent SDK의 `canUseTool` 콜백으로 질문을 가로채 프로그램이 답을 돌려줄 수 있다. 질문을 다른 사람에게 보내는 공식 접점이다 | [Agent SDK 사용자 입력](https://code.claude.com/docs/en/agent-sdk/user-input) |

정리하면, **역할을 나눈 에이전트 병렬 개발은 Claude Code가 이미 하고 있고, 질문을 정할 권한이 있는 다른 사람에게 보내는 일은 구조적으로 하지 않는다.** NOMOS가 차별점을 주장할 수 있는 자리는 뒤쪽이다.

### "묻게 하라" 쪽의 흐름

블로그와 강의에서는 반대 방향의 이야기도 많다. 기능을 만들기 전에 "AskUserQuestion으로 나를 인터뷰해라"라고 시켜 명세를 다듬는 방식이 널리 퍼졌다. 한 줄짜리 요구사항에서 수십 개의 질문이 나왔다는 사례도 있다([torq software 블로그](https://torqsoftware.com/blog/2026/2026-01-14-claude-ask-user-question/)). 질문이 많아질수록 "누가 답할 것인가"의 비용도 커진다.

### 멀티 에이전트 자체에 대한 논쟁

2025년 6월 Cognition이 "멀티 에이전트를 만들지 마라"는 글에서 맥락이 나뉘면 하위 에이전트들이 서로 다른 가정으로 일을 해 결과가 어긋난다고 주장했다. 다음 날 Anthropic은 서브에이전트마다 따로 맥락을 주는 연구 시스템이 단일 에이전트보다 넓은 조사에서 낫다는 글을 냈다. LangChain의 정리는 "읽기는 병렬화하기 쉽고 쓰기는 어렵다. 쓰기가 충돌하면 결과가 나빠진다"였다([LangChain 블로그](https://blog.langchain.com/how-and-when-to-build-multi-agent-systems)).

이 논쟁은 NOMOS에 그대로 적용된다. 프론트와 백엔드 에이전트가 동시에 코드를 쓰는 일은 Cognition이 경고한 상황이다. 서로 다른 가정을 막는 장치가 바로 **먼저 합의한 최소 계약**과 **정할 권한이 있는 사람에게 가는 질문**이다. 그래서 이 두 가지가 이번 학기의 1차 목표가 된다.

에이전트끼리 토론시키면 나아진다는 주장도 냉정하게 볼 필요가 있다. NeurIPS 2025 논문 "Debate or Vote"는 7개 벤치마크에서 멀티 에이전트 토론의 이득 대부분이 단순 다수결에서 나오고, 토론 자체는 기대 정확도를 올리지 않는다고 보였다([arXiv 2508.17536](https://arxiv.org/abs/2508.17536)). 비판 전용 에이전트를 붙이는 계획을 뒤로 미루는 이유 중 하나다.

### 우리 팀이 실제로 받은 질문

맥미니 한 대의 Claude Code 세션 기록(2026-05-21 ~ 10-12)에서 AskUserQuestion 질문 220개를 뽑았다. 그중 173개는 Jazzify라는 실제 팀 프로젝트에서 나왔다. 이 팀은 프론트엔드와 백엔드를 다른 사람이 맡고, 프론트가 백엔드에 요구사항 문서를 올리는 방식으로 일한다. 이 맥미니의 주인은 프론트 담당이다.

<!-- stats -->

- 220 | 추출한 질문(답이 있는 것 215)
- 77.5% | 추천 선택지를 그대로 고른 비율(110/142)
- 68% | 첫 번째 선택지를 고른 비율
- 104초 | 답까지 걸린 시간 중앙값, p90 약 31분

<!-- /stats -->

질문마다 "이 팀이 PM, FE, BE 3인 팀이었다면 누가 정할 결정인가"를 붙였다. 결정 유형(우선순위, 범위, 제품 정책, 화면, API 계약, 자기 구현, 환경과 배포, 요청 의도 확인)도 함께 붙였다.

<!-- chart:owner-dist -->

| 1순위 owner | FE 에이전트 질문(133) | BE 에이전트 질문(40) | 합계 |
| --- | --- | --- | --- |
| PM(대표) | 81 | 22 | 103 (60%) |
| 자기 소관 | 43 | 17 | 60 (35%) |
| 상대 기술 역할 | 9 | 1 | 10 (6%) |

눈에 띄는 점이 셋 있다.

- **우선순위를 묻는 질문이 32개나 된다.** "이 백엔드 요구사항 문서를 몇 순위로 올릴까요?" 같은 질문이다. 개발자 개인이 아니라 대표가 정할 일이다.
- **요청 의도를 되묻는 질문이 27개다.** "말씀하신 상단바가 어느 화면인가요?" 같은 질문은 그 일을 시킨 사람만 답할 수 있다.
- **선택지에 "백엔드에 판단 위임"이 직접 나온 질문이 있다.** 프론트 에이전트가 이미 자기 소관이 아님을 알면서도 프론트 개발자에게 물은 경우다.

이 숫자는 Claude가 붙인 임시 라벨이고, 한 사람의 세션이라는 한계가 있다. 그래도 기획 단계에서 가정한 "FE와 BE 사이의 질문 라우팅"이 전체의 작은 부분이고, 대표에게 가야 할 질문이 훨씬 많다는 방향은 뚜렷하다.

## 4. 실험: owner 배정은 얼마나 정확하게 되나

### 무엇을 비교했나

같은 질문을 여러 라우터에 넣고, 첫 수신자가 그 결정을 정할 권한이 있는 사람인지 쟀다. 평가 세트는 다섯 가지이고 합치지 않고 따로 본다.

| 세트 | 문항 | 정답을 붙인 사람 | 특징 |
| --- | --- | --- | --- |
| 실제 팀 질문 | 173 | Claude(임시, 사람 검수 전) | 문장이 길고 맥락에 기댄다. 가장 현실적이다 |
| 백엔드 20문항 | 20 | NOMOS 백엔드 담당 | 질문 중계 실험에서 나온 질문 10개와 만든 질문 10개. 역할이 FE와 BE뿐이다 |
| 정원 마감 합성 | 24 | Claude | "정원이 차면 신청하지 못하게 해" 시나리오 |
| 결제 환불 보류 세트 | 32 | Claude, 개선안을 만들기 전에 고정 | 처음 보는 도메인. 레포 경로 소유 표를 상황에 넣었다 |
| 초대 수락 어려운 보류 세트 | 30 | Claude, 라우터 실행 전에 고정 | 위 세트가 너무 쉬워 새로 만들었다. 기술적이지만 자기 소관인 질문, BE가 묻는 소비자 요구, 운영 반영을 섞었다 |

라우터는 여섯 종류다. 지금 서버 기본값인 반대 역할 규칙, 전부 PM에게 보내기, 키워드 규칙, LLM이 결정 유형만 분류하고 owner는 팀 표로 정하는 방식, LLM이 owner를 직접 고르는 방식(v1), 그리고 v1의 오답을 보고 경계 규칙을 더한 v2다. LLM은 haiku와 sonnet을 썼다.

> LLM 라우터는 정답을 볼 수 없게 막은 별도 에이전트가 문항만 읽고 판정했다. 연구 허브의 `claude -p` 경로는 실험 당일 구독 주간 한도에 걸려 쓰지 못했다. 그래서 지연과 비용은 운영 조건과 달라 이 표에 싣지 않는다.

### 읽는 법

- **현재 서버 기본값은 실제 질문에서 거의 쓸모가 없다(13.3%).** FE와 BE 질문만 있는 백엔드 20문항에서는 70%였다. 설계 가정이 데이터와 달랐던 것이다.
- **키워드 규칙은 익숙한 데이터에서만 통한다.** 실제 질문 78%에서 처음 보는 결제 환불 세트 53%로 떨어졌다. 규칙을 Jazzify 문장에 맞춰 만들었기 때문이다.
- **LLM이 owner를 직접 고르는 쪽이 가장 낫다.** v1 sonnet이 실제 질문 94.2%, 백엔드 20문항 95%였다. 우리가 처음 밀었던 "유형 분류 + 팀 표"는 실제 질문에서는 비슷했지만 백엔드 20문항(85%)과 정원 마감(87.5%)에서 뒤졌다. "화면에 어떤 필드가 필요한가요?" 같은 소비자 요구를 API 계약으로 분류해 BE 자기 소관으로 보낸 것이 주된 원인이다.
- **v2는 낙관적으로 읽어야 한다.** v2 규칙(소비자 요구는 소비자에게, 응답 모양은 제공자에게, 운영 반영은 무조건 PM에게, 남의 파일은 소유 역할에게, 확신이 없어도 PM으로 몰지 않기)은 실제 질문의 오답을 보고 만들었다. 실제 질문 98.3%는 같은 데이터에서 잰 숫자다. 처음 보는 두 보류 세트(62문항)를 합치면 sonnet은 v1과 v2 모두 61/62로 같았고, haiku만 60/62에서 61/62로 한 문항 나아졌다. 일부러 어렵게 만든 초대 수락 세트에서도 LLM은 93~100%였다. **우리가 만든 합성 질문은 아무리 꼬아도 LLM에게 쉽다.** 진짜 시험대는 맥락에 기대는 실제 팀 질문이고, 그래서 사람 검수와 실제 팀 로그가 필요하다.
- **정확도만 보면 "전부 PM에게"도 80%다.** PM이 정해도 되는 질문이 많아서다. 그래서 대표에게 보낸 비율을 같이 봐야 한다. v1 sonnet은 73.4%를 대표에게 보냈고, v2 sonnet은 65.9%로 정답 분포(59.5%)에 가까워졌다.

- 실제 질문에서 LLM이 반대 역할 규칙과 키워드 규칙보다 낫다는 것은 통계적으로 분명하다.
- **백엔드 20문항의 "95% 대 70%"는 구간이 겹친다.** 표본이 작아서 이 세트만으로는 차이를 주장할 수 없다.
- 직접 지정과 유형 분류의 차이, sonnet과 haiku의 차이는 한 번 돌린 결과로는 실제 질문에서 유의하지 않다.
- **다만 haiku는 판정이 흔들린다.** 같은 haiku 라우터를 같은 조건으로 한 번 더 돌리자 실제 질문의 21.4%에서 판정이 바뀌었고, 두 번째 정확도는 86.7%였다(첫 번째 91.3%). 바뀐 판정 대부분(26건)은 PM과 자기 소관 사이였고, 바뀐 질문은 첫 실행 확신이 낮았다(중앙값 0.55, 전체 0.7). 백엔드 20문항에서는 5%만 바뀌었다. 같은 질문이 실행마다 다른 사람에게 가면 받는 사람이 혼란스럽다.
- **세 번 판정해 다수결을 내도 정확도는 오르지 않았다.** 세 번 각각 91.3%, 86.7%, 90.8%였고 다수결은 90.8%였다. 판정이 갈릴 때만 sonnet에게 다시 묻는 방식도 90.8%로, sonnet 한 번(94.2%)을 넘지 못했다. 대신 **세 번이 일치하는지가 쓸모 있는 신호였다.** 세 번 모두 같은 판정이 나온 질문(76%)은 93.9%가 맞았고, 갈린 질문(24%)은 81.0%만 맞았다. 갈리는 질문은 모델을 더 불러도 잘 안 풀리는 어려운 질문이라, 받는 사람에게 "확인 필요"로 표시하고 넘기기를 쉽게 해 주는 데 쓰는 게 맞다. 이 측정은 에이전트 한 번에 문항 전체를 판정시킨 방식이라 운영 경로(질문마다 한 번씩)와 다를 수 있어, 기말에 운영 경로로 다시 잰다.

실제 질문과 백엔드 20문항에서 골랐다. 프로젝트 고유 이름은 일반적인 말로 바꿨다.

| "이 요구사항 문서를 몇 순위(P1~P5)로 올릴까요?" | FE | PM | BE, 틀림 | PM, 맞음(확신 0.9) |

반대 역할 규칙은 FE와 BE 사이의 질문(아래 네 줄)에서는 잘 맞고, 대표에게 가야 할 질문(위 두 줄)에서는 늘 틀린다. LLM은 그 반대다. **실제 질문에서 LLM 직접 v1이 틀린 10개 중 9개는 확신 0.6 이하에서 대표에게 미룬 경우였다.** 모르면 대표에게 보내는 습관이 대표 부하의 원인이다. v2에 "확신이 없어도 대표로 몰지 말고 가장 그럴듯한 쪽을 고른 뒤 확신을 낮게 줘라"를 넣은 이유이고, 파일 소유자 질문은 LLM보다 경로 소유권 규칙이 정확하다.

### 확신도가 낮으면 대표에게: 효과 없음

기획안에는 "LLM의 확신도가 낮으면 사람(대표)에게 일임한다"는 단계가 있었다. 확신도 문턱 아래 질문을 대표에게 보내면 어떻게 되는지 쟀다.

| 라우터 | 문턱 | 첫 수신자 정확도 | 대표 부담 |
| --- | --- | --- | --- |
| LLM 직접 지정 v1(sonnet), 문턱 없음 | - | 94.2% | 73.4% |
| 같은 라우터 | 0.6 | 93.1% | 84.4% |
| 같은 라우터 | 0.8 | 89.6% | 89.6% |
| 같은 라우터 | 0.9 | 84.4% | 96.0% |

모든 라우터에서 같은 모양이었다. 확신이 낮은 질문도 LLM의 1순위가 대표보다 더 자주 맞았다. 그래서 7절의 제안에서는 확신이 낮을 때 대표에게 몰지 않고 1순위 후보에게 보내되 버튼 하나로 넘길 수 있게 바꿨다.

### 오류를 5% 이하로 지키며 자동으로 보낼 수 있는 몫

확신도가 높은 순서로 자동 배정하고 나머지는 사람이 나눠 준다고 할 때, 자동 배정한 몫의 오류가 5%를 넘지 않는 최대 비율이다. v1 sonnet 98.3%, v1 haiku 86.1%, 유형 분류 sonnet 83.8%, 유형 분류 haiku 50.3%였다. 작은 모델이 자기 확신도를 덜 정확하게 매긴다는 뜻이다. 비용 때문에 haiku를 쓰려면 확신도 보정이 따로 필요하다.

### 이전 결과와의 관계

연구 허브의 M2는 사람 PR 리뷰에서 뽑은 결정 1,984건을 다섯 역할(대표, 백엔드, 프론트엔드, 디자인, 데브옵스) 중 하나로 배정하는 문제였고, haiku 75%, 임베딩 65%, 규칙 60%였다(연구 허브 `reports/rq2_routing.md`). 이번에는 역할이 셋이고 질문이 에이전트의 실제 문장이라 문제가 더 쉽다. 역할을 늘리면 정확도가 내려간다는 점은 미리 알고 가야 한다.

## 5. 냉정한 판단

### 새롭지 않은 것

| 기획안의 아이디어 | 이미 있는 것 |
| --- | --- |
| PM이 요구사항을 정하고 API 명세를 먼저 만든 뒤 FE와 BE를 병렬로 돌린다 | MetaGPT(ICLR 2024, [arXiv 2308.00352](https://arxiv.org/abs/2308.00352))가 제품 관리자, 설계자, 엔지니어 순서의 표준 작업 절차로 했다. Claude Code agent teams도 FE와 BE 팀원을 예로 든다 |
| 최소 공통 계약을 먼저 합의하고 병렬 개발 | 계약 우선 개발(OpenAPI 우선 설계, 소비자 주도 계약 테스트)은 사람 팀에서 오래된 관행이다 |
| 비판 전용 에이전트, ERD 에이전트, 스케줄러 에이전트 | 생성과 검증 분리(LLM-as-a-Judge)는 흔하다. 역할을 더 늘리면 토큰은 늘고 이득은 불확실하다(Debate or Vote) |
| 결정 모델로 owner를 빠르게 고른다 | Jev(TypeSafe AI, 2026-09-15 공개)가 "System 1" 결정 모델로 나왔다. 회사 자체 벤치마크에서 정확도는 최신 LLM보다 몇 점 낮고 대신 빠르고 싸다고 한다(독립 검증 없음, [소개 글](https://www.datacamp.com/blog/system-one-models-jev)) |

### 새로운 것

- **여러 사람이 각자 노트북에서 돌리는 에이전트의 질문을, 서버가 정할 권한이 있는 사람에게 보내고 답을 같은 실행으로 돌려준다.** Claude Code는 한 사람, 한 세션 안에서만 팀을 꾸린다. 사람 팀의 버그 트리아지 연구는 많지만, AI 에이전트의 질문을 역할별 사람에게 보내는 과정을 측정한 공개 데이터는 찾지 못했다(NOMOS 연구 허브 데이터 지도).
- **질문, 배정, 답, 대기 시간을 이벤트로 남긴다.** 이 로그가 쌓이면 그 자체로 공개된 적 없는 데이터가 된다.

### 기술적으로 되는가

된다. 그리고 대부분은 이미 만들었다. NOMOS 백엔드에는 질문 중계가 들어가 있다(마이그레이션 018).

- Executor가 Claude Code를 `--permission-prompt-tool`로 띄워 AskUserQuestion을 가로채고, 서버가 owner를 정해 답을 받으면 같은 실행에서 이어 간다. 3분 안에 답이 없으면 태스크를 내려놓고, 답이 오면 다시 가져간다. 3일이 지나면 만료되어 대표에게 올라간다.
- 답할 역할의 노트북이 자기 코드를 읽기 전용으로 살펴 답 초안을 내는 상담 실행이 있다. 코드에 이미 정해진 답이면 사람을 부르지 않는다. 애매한 레포와 지시 주입 질문으로 만든 시험 26회에서 틀린 확정 0회, 지시 따름 0회, 비밀 유출 0회였다(백엔드 실험 A1, A2).
- 라우터는 인터페이스로 분리돼 있어 규칙, LLM, Jev를 바꿔 끼울 수 있다. 라우터가 실패하거나 30초를 넘기면 규칙 라우터로 대체하고 그 사실을 기록한다.
- 프로젝트마다 질문 중계를 끌 수 있어서, 끈 상태가 곧 대조군이 된다.

### 남은 위험

- **3인 팀은 문제가 쉽다.** 무작위로 골라도 33%다. 수천 명 중에서 담당자를 찾는 버그 트리아지와 같은 선상에서 비교하면 안 된다.
- **대표가 병목이 된다.** 질문의 60%가 대표 소관이라는 결과는 거꾸로 말하면 대표의 시간이 가장 비싼 자원이라는 뜻이다. owner를 맞히는 것보다 대표에게 가는 질문을 줄이는 쪽(결정 장부 재사용, 추천을 받아들이고 진행 후 확인)이 체감 효과가 더 클 수 있다.
- **정답 라벨이 아직 사람 검수 전이다.** 기말까지 팀원 세 명이 블라인드로 다시 붙여 일치도를 내야 숫자를 주장할 수 있다.
- **답을 기다리는 시간은 라우팅으로 줄지 않는다.** 맞는 사람에게 가도 그 사람이 자리에 없으면 기다린다. 대기 중앙값 104초, p90 31분이라는 분포가 그 상한을 보여 준다.

## 6. 두 번째 축: 공통 계약 위에서 병렬로

교수님이 짚은 1차 목표는 둘이다. 할당이 맞게 되는가, 그리고 공통 프로토콜을 지키면서 병렬 개발이 되는가. 앞 절들이 첫째를 다뤘다면 이 절은 둘째다.

### 계약은 생각보다 자주 깨진다

| 근거 | 결과 |
| --- | --- |
| 공개 웹앱 레포 8개의 OpenAPI 스펙 변경 146쌍(NOMOS 연구 허브 M4, oasdiff) | 스펙을 바꾼 커밋의 46%(95% 구간 38~54%)에 깨지는 변경이 하나 이상 있었다 |
| 같은 레포들의 사람 리뷰 코멘트 중 FE와 BE 계약 불일치 언급(M4) | 1.6~8.4%(두 모델 라벨의 범위). 불일치를 깨뜨린 쪽은 백엔드가 74% |

계약은 한 번 정하고 끝나는 문서가 아니라 계속 흔들린다. 그리고 흔드는 쪽은 대개 제공자(백엔드)다. FE와 BE 에이전트가 동시에 일하면 이 흔들림이 더 빨라진다.

### NOMOS가 가진 장치와 상태

| 장치 | 하는 일 | 상태 |
| --- | --- | --- |
| 최소 계약 먼저(PM 선행 규칙) | 계약만 보고 만들 수 있는 일은 선행을 걸지 않고 병행한다. 계약을 먼저 정해야 하는데 명세에 다 못 적으면 "계약 확정" 태스크로 쪼개고 상대는 그 태스크에만 선행을 건다 | 동작(PM 지침) |
| 결정 기록 | 확정된 계약은 DECIDED 노트로 프로젝트 전체에 전달한다. 남의 소관을 가정했으면 DECIDED가 아니라 "가정함, 확인 필요" 노트로 남긴다(지어낸 계약을 DECIDED로 발행한 실험 결과에서 나온 규칙) | 동작 |
| 경로 소유권과 실제 diff 검사(V3) | 남의 영역 파일을 고친 커밋은 제출 단계에서 반려된다. 신고와 실제 diff가 다르면 실패 | 동작 |
| 계약 대조(V1A) | 실제 응답의 스키마, 상태 코드, 필드명을 OpenAPI 계약과 기계적으로 비교한다 | **비어 있음.** 계약을 담을 테이블이 없어 항상 SKIPPED |
| 질문 중계 | 계약에 없는 결정은 정할 권한이 있는 사람에게 묻는다 | 동작(이 문서의 주제) |

### 판단

- **"최소 계약을 먼저 확정하고 병렬로"는 이미 PM 지침에 들어 있다.** 새로 만들 것은 많지 않다.
- **가장 큰 빈칸은 계약 대조(V1A)다.** 이게 꺼져 있으면 에이전트가 계약을 지켰는지 서버가 모르고, 기말 실험의 "결정 재작업" 지표도 사람이 손으로 세야 한다. 연구 허브에 oasdiff 기반 비교가 이미 있으므로, 계약 저장과 응답 대조를 붙이는 일이 기말까지 백엔드 쪽 최우선 과제다.
- 깨뜨리는 쪽이 대개 제공자라는 M4 결과는 질문 라우팅과도 이어진다. 계약을 바꾸려는 쪽이 먼저 소비자에게 묻게 하면(BE가 "화면에 이 필드가 필요한가요?"를 FE에게) 깨짐을 미리 막을 수 있다. 이번 실험에서 LLM이 가장 자주 틀린 유형이 바로 이 "소비자 요구" 질문이었다.

## 7. 제안: owner 배정 다섯 단계

실험 결과를 반영해 기획안의 "LLM 확신도가 낮으면 일임" 구조를 아래처럼 바꾼다.

| 단계 | 하는 일 | 근거 |
| --- | --- | --- |
| 0. 묻기 전에 | 명세, 결정 장부(DECIDED 노트), 코드에 답이 있으면 묻지 않는다. 상담 실행이 이미 이 일을 한다 | 상담 실행 26회 오류 0 |
| 1. 결정적 신호 먼저 | 경로 소유권(어느 역할이 그 파일을 소유하나), 운영 반영(배포, 운영 DB, 되돌리기 어려운 삭제)은 규칙으로 정한다. 운영 반영은 무조건 대표 승인 | 경로 소유권은 서버가 이미 안다. v1 LLM 오답의 상당수가 여기서 나왔다 |
| 2. LLM 라우터 | owner와 확신도를 낸다. 소비자 요구는 소비자에게, 응답 모양은 제공자에게 같은 경계 규칙을 프롬프트에 넣는다 | 실제 질문 94%, 백엔드 20문항 95% |
| 3. 확신이 낮을 때 | 대표에게 몰지 않고 1순위 후보에게 보내되, 받은 사람이 버튼 하나로 넘길 수 있게 한다 | "확신 낮으면 PM" 캐스케이드는 정확도를 낮추고 대표 부담만 늘렸다 |
| 4. 기록하고 배운다 | 넘기기는 곧 정답 라벨이다. 재배정 기록으로 프롬프트 예시와 팀 표를 고친다. 답은 결정 장부에 남겨 같은 질문에 자동으로 답한다 | 버그 트리아지 연구: 재배정 한 번에 평균 50일(Jeong 외, FSE 2009) |

## 9. 기말까지의 평가 계획

### 질문 두 개

- **할당이 맞게 되는가.** 팀원 세 명이 질문 300개(실제 질문 + 보류 세트 + 실험 중 생긴 질문)에 블라인드로 owner를 붙이고 일치도(카파)를 낸다. 라우터별 첫 수신자 정확도, 대표 부담, 넘기기 횟수, 질문에서 답까지 걸린 시간을 잰다.
- **공통 계약 위에서 병렬 개발이 되는가.** 같은 과제를 네 조건으로 돌린다.

| 조건 | 설명 |
| --- | --- |
| A | Claude Code 한 세션, 한 사람 |
| B | Claude Code agent teams, FE와 BE 팀원, 한 사람 |
| C | NOMOS, 질문 중계 끔(에이전트는 가정하고 진행, 대조군) |
| D | NOMOS, 질문 중계 켬 + owner 라우터 v2 + 최소 계약 먼저 |

지표는 네 개로 고정한다. 과제 성공(인수 테스트 통과), 끝날 때까지 걸린 시간, 토큰, 결정 때문에 생긴 재작업(계약 위반, 반려 횟수). 질문 관련 지표(정확도, 대표 부담, 대기 시간)는 C와 D 사이에서 본다.

### 일정(8주)

| 주 | 할 일 |
| --- | --- |
| 1~2 | 사람 검수 300문항, 라우터 v2를 서버 라우터 자리에 연결(설정으로 선택), 넘기기 버튼, 계약 대조(V1A) 켜기 |
| 3~4 | 과제 3개 확정(정원 마감, 결제 환불, 초대 수락), 조건 A~D 파이프라인과 로그 수집 |
| 5~6 | 본 실험, 결정 장부 재사용과 질문 묶기 추가 실험 |
| 7 | 분석, Jev 비교 한 번 |
| 8 | 기말 발표: 실측 표, 시연 |
