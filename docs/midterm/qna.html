중간발표 예상 질문과 답

발표 뒤 질의응답에서 나올 만한 질문 12개에 대한 짧은 답. 숫자는 조사 보고서(askuser-owner-report)와 같은 출처에서 나왔다. 답은 30초 안에 말할 수 있는 길이로 썼다.

2026년 10월최영현, 오영훈, 전병국데이터와 코드: NOMOS 연구 허브

데이터와 라벨

Q1. 정답 라벨을 Claude가 붙였는데 믿을 수 있나요? 아직은 임시 정답이라고 분명히 말씀드립니다. 같은 계열 모델 라우터에 유리할 수 있어서, 팀원 세 명이 같은 문항에 블라인드로 owner를 붙이는 검수 시트를 이미 만들어 두었습니다. 기말 전 첫 2주에 검수를 끝내고 일치도(카파)와 함께 숫자를 다시 냅니다. 백엔드 담당이 직접 정답을 붙인 20문항에서도 LLM이 95%였다는 점이 참고가 됩니다.

Q2. 질문 173개가 한 사람 세션에서 나온 건데 일반화할 수 있나요? 한계가 맞습니다. 다만 그 프로젝트는 FE와 BE를 다른 사람이 맡는 실제 팀이었고, FE 에이전트의 질문 중 "백엔드에 판단 위임"이 선택지로 나오는 등 팀 상황이 그대로 드러납니다. 기말에는 팀원 세션과 NOMOS 실험 로그에서 질문을 더 모읍니다.

Q3. 3인 팀이면 무작위로 골라도 33%인데 너무 쉬운 문제 아닌가요? 쉬운 쪽인 건 맞습니다. 그래서 무작위, 다수 클래스(전부 대표에게 80.3%), 규칙과 함께 비교했습니다. 핵심은 정확도보다 기획 단계의 가정이 틀렸다는 발견입니다. 질문의 60%가 대표 소관인데 지금 서버 라우터는 대표를 고를 수 없어 13.3%였습니다.

차별점

Q4. Claude Code agent teams도 FE, BE 팀원을 나눠서 병렬로 하는데 뭐가 다른가요? agent teams는 한 사람, 한 세션 안의 팀입니다. 팀원의 권한 요청도 리드 세션 한 곳으로 올라갑니다. NOMOS는 여러 사람이 각자 노트북에서 돌리는 에이전트를 서버가 묶고, 질문을 정할 권한이 있는 사람에게 보냅니다. 기말 실험에서 agent teams를 비교 조건(B)으로 직접 돌립니다.

Q5. PM이 API 명세를 먼저 만들고 병렬로 돌리는 건 MetaGPT도 했던데요? 맞습니다. 그래서 그 부분을 새롭다고 주장하지 않습니다. 저희가 보여 드리려는 건 여러 사람의 에이전트 질문을 owner에게 보내는 일과, 그 질문 로그 자체입니다.

방법

Q6. Jev 같은 결정 모델은 왜 안 썼나요? Jev는 9월에 나온 초기 모델이고 공개된 정확도가 회사 자체 벤치마크뿐입니다. 서버 라우터를 인터페이스로 분리해 두어서 바꿔 끼울 수 있고, 기말에 비교 실험 한 번으로 넣습니다. 지금 데이터로는 LLM이 이미 9할 이상이라 속도와 비용 쪽 이득을 보는 실험이 됩니다.

Q7. 확신도가 낮으면 사람에게 넘긴다고 하지 않았나요? 그렇게 계획했는데 실험해 보니 역효과였습니다. 확신도 0.8 아래를 대표에게 넘기면 첫 수신자 정확도가 94.2%에서 89.6%로 내려가고 대표 부담은 73.4%에서 89.6%로 늘었습니다. LLM이 틀린 10개 중 9개도 확신이 낮을 때 대표에게 미룬 경우였습니다. 그래서 1순위 후보에게 보내고 버튼 하나로 넘기게 바꿨습니다.

Q8. sonnet과 haiku 중 무엇을 쓸 건가요? 한 번 돌린 정확도는 통계적으로 차이가 없었지만(p=0.30), haiku는 같은 질문을 다시 넣으면 21%가 다른 사람에게 갔습니다. 세 번 다수결을 내도 정확도는 오르지 않았습니다. 지금은 sonnet을 기본으로 보고, 운영 경로에서 지연과 비용을 잰 뒤 정합니다.

범위와 계획

Q9. 공통 프로토콜은 어디까지 되어 있나요? "최소 계약을 먼저 정하고 병렬로"는 PM 지침에 이미 들어 있습니다. 확정된 계약을 알리는 노트, 남의 파일을 고치면 막는 검사도 동작합니다. 빈칸은 실제 응답을 OpenAPI 계약과 비교하는 검증 하나인데, 계약 저장소가 없어 꺼져 있습니다. 기말 전 첫 2주에 켭니다.

Q10. 대표가 병목이 되지 않나요? 그게 가장 큰 위험이라고 봅니다. 그래서 다음 아이디어를 대표의 시간을 아끼는 순서로 골랐습니다. 같은 결정을 다시 묻지 않게 결정 장부를 재사용하고, 같은 사람에게 가는 질문을 묶고, 추천 선택지를 받아들이고 진행한 뒤 확인만 받게 합니다(실제 질문에서 추천 수락률 77.5%).

Q11. 기말에는 무엇을 보여 주나요? 같은 과제를 네 조건으로 돌린 실측 표 하나입니다. Claude Code 한 세션, agent teams, NOMOS 질문 중계 끔, 켬. 지표는 과제 성공, 완료 시간, 토큰, 결정 때문에 생긴 재작업 네 개로 고정했습니다. 그리고 질문이 owner에게 가는 실제 시연입니다.

Q12. 합성 질문 결과는 왜 그렇게 높나요? 저희가 만든 질문이 LLM에게 쉽기 때문입니다. 일부러 어렵게 만든 세트에서도 93~100%가 나왔습니다. 그래서 합성 결과로 주장하지 않고, 실제 팀 질문과 사람 검수를 기말의 근거로 삼습니다.

이 문서의 숫자는 각 절에 출처를 붙였다. 예시값은 실측처럼 쓰지 않았다. 사람 검수 전 라벨에 기댄 숫자는 그렇게 표시했다.
