에이전트의 질문은 누구에게 가야 하는가

코딩 에이전트가 작업 중에 사람에게 묻는 질문(Claude Code의 AskUserQuestion)을, 여러 사람이 함께 개발하는 팀에서 그 결정을 내릴 권한이 있는 사람에게 바로 보내는 문제를 다룬다. 실제 질문 데이터, 사용자 커뮤니티의 논의, 공개 연구, 그리고 우리가 직접 돌린 라우터 비교 실험을 바탕으로 이 방향이 의미가 있는지, 기술적으로 되는지, 무엇은 새롭지 않은지를 정리했다.

2026년 10월최영현, 오영훈, 전병국데이터와 코드: NOMOS 연구 허브

  1. Claude Code의 질문 채널은 구조적으로 한 사람에게만 간다. 서브에이전트는 질문 도구를 쓸 수 없고, 실험 기능인 agent teams도 팀원의 권한 요청을 리드 세션 한 곳으로 올린다. 여러 사람이 각자 에이전트를 돌리는 팀에서 "이 질문은 백엔드 담당이 정할 일"이라는 개념 자체가 없다.
  2. 질문의 다수는 프론트와 백엔드 사이가 아니라 대표(PM) 소관이다. 실제 팀 세션에서 나온 질문 173개를 라벨링해 보니 1순위 owner가 PM인 질문이 60%, 자기 소관이 35%, 상대 기술 역할 소관은 6%였다. 지금 서버의 기본 라우터는 PM을 고를 수 없어서 13%만 맞혔다.
  3. owner 배정 자체는 어렵지 않다. LLM이 직접 고르면 실제 질문 94%, 백엔드 팀이 정답을 붙인 20문항 95%를 맞혔다. 키워드 규칙은 익숙한 데이터에서는 78%였지만 처음 보는 도메인에서는 53%로 떨어졌다.
  4. 진짜 어려운 부분은 정확도가 아니라 대표에게 몰리는 부하와 답을 기다리는 시간이다. 가장 정확한 라우터도 질문의 73%를 대표에게 보냈다. 기획안에 있던 "확신이 낮으면 대표에게"라는 단계는 오히려 첫 수신자 정확도를 떨어뜨렸다.
  5. 그래서 이번 학기 목표는 "3역할 팀에서 할당이 맞게 되는가"와 "공통 계약 위에서 병렬 개발이 되는가" 두 가지로 좁힌다. 역할을 더 쪼개거나 비판, ERD, 스케줄러 에이전트를 붙이는 일은 뒤로 미룬다. 교수님 피드백과 같은 결론이다.

이 문서의 숫자에는 출처를 붙였다. 기획 단계 표에 있던 "일반 에이전트 42%, NOMOS 91%" 같은 값은 예시값이라 쓰지 않았다. 실제 질문 라벨은 Claude가 붙인 임시 정답이고 사람 검수 전이다. 같은 계열 모델 라우터에 유리할 수 있다.

1. 문제: 질문은 한 줄로만 흐른다

AskUserQuestion은 Claude Code가 작업 중에 사람에게 선택지를 주고 묻는 도구다. 질문 1~4개, 선택지 2~4개를 한 번에 보내고, 사람이 고른 답을 받아 같은 작업을 이어 간다(Agent SDK 문서).

혼자 쓸 때는 이 구조가 자연스럽다. 질문을 받는 사람이 곧 결정권자이기 때문이다. 문제는 여러 사람이 각자 에이전트를 돌리는 팀이다. 프론트엔드 개발자의 에이전트가 "정원이 찬 스터디에 신청하면 서버가 어떤 에러 코드를 주나요?"라고 물으면, 그 질문은 프론트엔드 개발자 화면에 뜬다. 답할 권한도 정보도 없는 사람이 메신저로 백엔드 개발자를 찾아가 묻고, 답을 받아 다시 입력한다.

Claude Code 공식 문서로 확인한 구조는 이렇다.

사실 출처
서브에이전트에서는 AskUserQuestion을 쓸 수 없다. 질문은 메인 세션을 운영하는 사람에게만 간다 Agent SDK 사용자 입력
agent teams(실험 기능)에서 팀원의 권한 요청은 리드 세션으로 올라가고, 팀 전체가 한 사람의 한 세션 안에 있다. 팀은 세션마다 하나이고 세션끼리 공유할 수 없다 agent teams 문서
같은 문서가 "프론트엔드, 백엔드, 테스트를 각각 다른 팀원이 맡는 계층 간 조율"을 대표 사용 예로 든다. 역할을 나눈 병렬 개발 자체는 이미 제품 기능이다 같은 문서
질문에 시간 제한(askUserQuestionTimeout)을 걸면, 시간이 지나 Claude가 스스로 판단해 진행하고 나중에 다시 물을 수 있다 도구 레퍼런스
Agent SDK의 canUseTool 콜백으로 질문을 가로채 프로그램이 답을 돌려줄 수 있다. 질문을 다른 사람에게 보내는 공식 접점이다 Agent SDK 사용자 입력

정리하면, 역할을 나눈 에이전트 병렬 개발은 Claude Code가 이미 하고 있고, 질문을 정할 권한이 있는 다른 사람에게 보내는 일은 구조적으로 하지 않는다. NOMOS가 차별점을 주장할 수 있는 자리는 뒤쪽이다.

2. 사용자들은 무엇을 이야기하고 있나

질문 도구를 둘러싼 이슈

Claude Code 저장소에는 AskUserQuestion을 언급한 이슈가 1,205건 있다(2026-10-03 검색, NOMOS 연구 허브). 성격이 분명한 것들을 골랐다.

이슈 내용 우리에게 주는 뜻
#12890, #34592 서브에이전트에서 질문 도구가 설정과 상관없이 빠져 있다. 문서에는 전달된다고 쓰여 있어 혼란이 크다 멀티 에이전트에서 질문을 어떻게 흘릴지 공식 답이 아직 없다

#50728 터미널 없는 헤드리스 실행에서는 질문이 빈 답으로 바로 끝난다(해결 안 함으로 닫힘) 서버에서 에이전트를 돌리려면 질문을 받아 줄 자리를 직접 만들어야 한다. NOMOS가 실제로 부딪힌 문제다
#70648 원격 세션에서 쉬었다 돌아오면 같은 질문에 2~7번 답해야 한다 비동기로 답하는 상황(답할 사람이 자리에 없음)을 제품이 아직 잘 다루지 못한다
spec-kit #2181 명세 도구가 번호 목록 대신 네이티브 질문 도구를 쓰게 해 달라는 요청 질문이 명세 작성의 핵심 단계로 쓰이고 있다
템플릿 PR #54 agent teams에서 막힌 팀원의 질문을 리드에게 보고하고, 리드가 AskUserQuestion으로 바꿔 묻게 하는 공동체 패턴 "질문을 중계한다"는 발상은 이미 사용자들이 손으로 하고 있다. 다만 받는 사람은 여전히 한 명이다

"묻게 하라" 쪽의 흐름

블로그와 강의에서는 반대 방향의 이야기도 많다. 기능을 만들기 전에 "AskUserQuestion으로 나를 인터뷰해라"라고 시켜 명세를 다듬는 방식이 널리 퍼졌다. 한 줄짜리 요구사항에서 수십 개의 질문이 나왔다는 사례도 있다(torq software 블로그). 질문이 많아질수록 "누가 답할 것인가"의 비용도 커진다.

멀티 에이전트 자체에 대한 논쟁

2025년 6월 Cognition이 "멀티 에이전트를 만들지 마라"는 글에서 맥락이 나뉘면 하위 에이전트들이 서로 다른 가정으로 일을 해 결과가 어긋난다고 주장했다. 다음 날 Anthropic은 서브에이전트마다 따로 맥락을 주는 연구 시스템이 단일 에이전트보다 넓은 조사에서 낫다는 글을 냈다. LangChain의 정리는 "읽기는 병렬화하기 쉽고 쓰기는 어렵다. 쓰기가 충돌하면 결과가 나빠진다"였다(LangChain 블로그).

이 논쟁은 NOMOS에 그대로 적용된다. 프론트와 백엔드 에이전트가 동시에 코드를 쓰는 일은 Cognition이 경고한 상황이다. 서로 다른 가정을 막는 장치가 바로 먼저 합의한 최소 계약과 정할 권한이 있는 사람에게 가는 질문이다. 그래서 이 두 가지가 이번 학기의 1차 목표가 된다.

에이전트끼리 토론시키면 나아진다는 주장도 냉정하게 볼 필요가 있다. NeurIPS 2025 논문 "Debate or Vote"는 7개 벤치마크에서 멀티 에이전트 토론의 이득 대부분이 단순 다수결에서 나오고, 토론 자체는 기대 정확도를 올리지 않는다고 보였다(arXiv 2508.17536). 비판 전용 에이전트를 붙이는 계획을 뒤로 미루는 이유 중 하나다.

우리 팀이 실제로 받은 질문

맥미니 한 대의 Claude Code 세션 기록(2026-05-21 ~ 10-12)에서 AskUserQuestion 질문 220개를 뽑았다. 그중 173개는 Jazzify라는 실제 팀 프로젝트에서 나왔다. 이 팀은 프론트엔드와 백엔드를 다른 사람이 맡고, 프론트가 백엔드에 요구사항 문서를 올리는 방식으로 일한다. 이 맥미니의 주인은 프론트 담당이다.

눈에 띄는 점이 셋 있다.

  • 우선순위를 묻는 질문이 32개나 된다. "이 백엔드 요구사항 문서를 몇 순위로 올릴까요?" 같은 질문이다. 개발자 개인이 아니라 대표가 정할 일이다.
  • 요청 의도를 되묻는 질문이 27개다. "말씀하신 상단바가 어느 화면인가요?" 같은 질문은 그 일을 시킨 사람만 답할 수 있다.
  • 선택지에 "백엔드에 판단 위임"이 직접 나온 질문이 있다. 프론트 에이전트가 이미 자기 소관이 아님을 알면서도 프론트 개발자에게 물은 경우다.

이 숫자는 Claude가 붙인 임시 라벨이고, 한 사람의 세션이라는 한계가 있다. 그래도 기획 단계에서 가정한 "FE와 BE 사이의 질문 라우팅"이 전체의 작은 부분이고, 대표에게 가야 할 질문이 훨씬 많다는 방향은 뚜렷하다.

4. 실험: owner 배정은 얼마나 정확하게 되나

무엇을 비교했나

같은 질문을 여러 라우터에 넣고, 첫 수신자가 그 결정을 정할 권한이 있는 사람인지 쟀다. 평가 세트는 네 가지이고 합치지 않고 따로 본다.

세트 문항 정답을 붙인 사람 특징
실제 팀 질문 173 Claude(임시, 사람 검수 전) 문장이 길고 맥락에 기댄다. 가장 현실적이다
백엔드 20문항 20 NOMOS 백엔드 담당 질문 중계 실험에서 나온 질문 10개와 만든 질문 10개. 역할이 FE와 BE뿐이다
정원 마감 합성 24 Claude "정원이 차면 신청하지 못하게 해" 시나리오
결제 환불 보류 세트 32 Claude, 개선안을 만들기 전에 고정 처음 보는 도메인. 레포 경로 소유 표를 상황에 넣었다

라우터는 여섯 종류다. 지금 서버 기본값인 반대 역할 규칙, 전부 PM에게 보내기, 키워드 규칙, LLM이 결정 유형만 분류하고 owner는 팀 표로 정하는 방식, LLM이 owner를 직접 고르는 방식(v1), 그리고 v1의 오답을 보고 경계 규칙을 더한 v2다. LLM은 haiku와 sonnet을 썼다.

LLM 라우터는 정답을 볼 수 없게 막은 별도 에이전트가 문항만 읽고 판정했다. 연구 허브의 claude -p 경로는 실험 당일 구독 주간 한도에 걸려 쓰지 못했다. 그래서 지연과 비용은 운영 조건과 달라 이 표에 싣지 않는다.

실제 질문의 정답 분포에서 PM이 1순위인 비율은 59.5%다.

읽는 법

  • 현재 서버 기본값은 실제 질문에서 거의 쓸모가 없다(13.3%). FE와 BE 질문만 있는 백엔드 20문항에서는 70%였다. 설계 가정이 데이터와 달랐던 것이다.
  • 키워드 규칙은 익숙한 데이터에서만 통한다. 실제 질문 78%에서 처음 보는 결제 환불 세트 53%로 떨어졌다. 규칙을 Jazzify 문장에 맞춰 만들었기 때문이다.
  • LLM이 owner를 직접 고르는 쪽이 가장 낫다. v1 sonnet이 실제 질문 94.2%, 백엔드 20문항 95%였다. 우리가 처음 밀었던 "유형 분류 + 팀 표"는 실제 질문에서는 비슷했지만 백엔드 20문항(85%)과 정원 마감(87.5%)에서 뒤졌다. "화면에 어떤 필드가 필요한가요?" 같은 소비자 요구를 API 계약으로 분류해 BE 자기 소관으로 보낸 것이 주된 원인이다.
  • v2는 낙관적으로 읽어야 한다. v2 규칙(소비자 요구는 소비자에게, 응답 모양은 제공자에게, 운영 반영은 무조건 PM에게, 남의 파일은 소유 역할에게, 확신이 없어도 PM으로 몰지 않기)은 실제 질문의 오답을 보고 만들었다. 실제 질문 98.3%는 같은 데이터에서 잰 숫자다. 처음 보는 보류 세트에서는 v1과 차이가 없었다(100%, 96.9%). 보류 세트가 너무 명확해서 변별력이 없었던 것도 이유다. 사람 검수와 새 질문으로 다시 재야 한다.
  • 정확도만 보면 "전부 PM에게"도 80%다. PM이 정해도 되는 질문이 많아서다. 그래서 대표에게 보낸 비율을 같이 봐야 한다. v1 sonnet은 73.4%를 대표에게 보냈고, v2 sonnet은 65.9%로 정답 분포(59.5%)에 가까워졌다.

확신도가 낮으면 대표에게: 효과 없음

기획안에는 "LLM의 확신도가 낮으면 사람(대표)에게 일임한다"는 단계가 있었다. 확신도 문턱 아래 질문을 대표에게 보내면 어떻게 되는지 쟀다.

라우터 문턱 첫 수신자 정확도 대표 부담
LLM 직접 지정 v1(sonnet), 문턱 없음 - 94.2% 73.4%
같은 라우터 0.6 93.1% 84.4%
같은 라우터 0.8 89.6% 89.6%
같은 라우터 0.9 84.4% 96.0%

모든 라우터에서 같은 모양이었다. 확신이 낮은 질문도 LLM의 1순위가 대표보다 더 자주 맞았다. 그래서 6절의 제안에서는 확신이 낮을 때 대표에게 몰지 않고 1순위 후보에게 보내되 버튼 하나로 넘길 수 있게 바꿨다.

오류를 5% 이하로 지키며 자동으로 보낼 수 있는 몫

확신도가 높은 순서로 자동 배정하고 나머지는 사람이 나눠 준다고 할 때, 자동 배정한 몫의 오류가 5%를 넘지 않는 최대 비율이다. v1 sonnet 98.3%, v1 haiku 86.1%, 유형 분류 sonnet 83.8%, 유형 분류 haiku 50.3%였다. 작은 모델이 자기 확신도를 덜 정확하게 매긴다는 뜻이다. 비용 때문에 haiku를 쓰려면 확신도 보정이 따로 필요하다.

이전 결과와의 관계

연구 허브의 M2는 사람 PR 리뷰에서 뽑은 결정 1,984건을 다섯 역할(대표, 백엔드, 프론트엔드, 디자인, 데브옵스) 중 하나로 배정하는 문제였고, haiku 75%, 임베딩 65%, 규칙 60%였다(연구 허브 reports/rq2_routing.md). 이번에는 역할이 셋이고 질문이 에이전트의 실제 문장이라 문제가 더 쉽다. 역할을 늘리면 정확도가 내려간다는 점은 미리 알고 가야 한다.

5. 냉정한 판단

새롭지 않은 것

기획안의 아이디어 이미 있는 것
PM이 요구사항을 정하고 API 명세를 먼저 만든 뒤 FE와 BE를 병렬로 돌린다 MetaGPT(ICLR 2024, arXiv 2308.00352)가 제품 관리자, 설계자, 엔지니어 순서의 표준 작업 절차로 했다. Claude Code agent teams도 FE와 BE 팀원을 예로 든다
최소 공통 계약을 먼저 합의하고 병렬 개발 계약 우선 개발(OpenAPI 우선 설계, 소비자 주도 계약 테스트)은 사람 팀에서 오래된 관행이다
비판 전용 에이전트, ERD 에이전트, 스케줄러 에이전트 생성과 검증 분리(LLM-as-a-Judge)는 흔하다. 역할을 더 늘리면 토큰은 늘고 이득은 불확실하다(Debate or Vote)
결정 모델로 owner를 빠르게 고른다 Jev(TypeSafe AI, 2026-09-15 공개)가 "System 1" 결정 모델로 나왔다. 회사 자체 벤치마크에서 정확도는 최신 LLM보다 몇 점 낮고 대신 빠르고 싸다고 한다(독립 검증 없음, 소개 글)

새로운 것

  • 여러 사람이 각자 노트북에서 돌리는 에이전트의 질문을, 서버가 정할 권한이 있는 사람에게 보내고 답을 같은 실행으로 돌려준다. Claude Code는 한 사람, 한 세션 안에서만 팀을 꾸린다. 사람 팀의 버그 트리아지 연구는 많지만, AI 에이전트의 질문을 역할별 사람에게 보내는 과정을 측정한 공개 데이터는 찾지 못했다(NOMOS 연구 허브 데이터 지도).
  • 질문, 배정, 답, 대기 시간을 이벤트로 남긴다. 이 로그가 쌓이면 그 자체로 공개된 적 없는 데이터가 된다.

기술적으로 되는가

된다. 그리고 대부분은 이미 만들었다. NOMOS 백엔드에는 질문 중계가 들어가 있다(마이그레이션 018).

  • Executor가 Claude Code를 --permission-prompt-tool로 띄워 AskUserQuestion을 가로채고, 서버가 owner를 정해 답을 받으면 같은 실행에서 이어 간다. 3분 안에 답이 없으면 태스크를 내려놓고, 답이 오면 다시 가져간다. 3일이 지나면 만료되어 대표에게 올라간다.
  • 답할 역할의 노트북이 자기 코드를 읽기 전용으로 살펴 답 초안을 내는 상담 실행이 있다. 코드에 이미 정해진 답이면 사람을 부르지 않는다. 애매한 레포와 지시 주입 질문으로 만든 시험 26회에서 틀린 확정 0회, 지시 따름 0회, 비밀 유출 0회였다(백엔드 실험 A1, A2).
  • 라우터는 인터페이스로 분리돼 있어 규칙, LLM, Jev를 바꿔 끼울 수 있다. 라우터가 실패하거나 30초를 넘기면 규칙 라우터로 대체하고 그 사실을 기록한다.
  • 프로젝트마다 질문 중계를 끌 수 있어서, 끈 상태가 곧 대조군이 된다.

남은 위험

  • 3인 팀은 문제가 쉽다. 무작위로 골라도 33%다. 수천 명 중에서 담당자를 찾는 버그 트리아지와 같은 선상에서 비교하면 안 된다.
  • 대표가 병목이 된다. 질문의 60%가 대표 소관이라는 결과는 거꾸로 말하면 대표의 시간이 가장 비싼 자원이라는 뜻이다. owner를 맞히는 것보다 대표에게 가는 질문을 줄이는 쪽(결정 장부 재사용, 추천을 받아들이고 진행 후 확인)이 체감 효과가 더 클 수 있다.
  • 정답 라벨이 아직 사람 검수 전이다. 기말까지 팀원 세 명이 블라인드로 다시 붙여 일치도를 내야 숫자를 주장할 수 있다.
  • 답을 기다리는 시간은 라우팅으로 줄지 않는다. 맞는 사람에게 가도 그 사람이 자리에 없으면 기다린다. 대기 중앙값 104초, p90 31분이라는 분포가 그 상한을 보여 준다.

6. 제안: owner 배정 다섯 단계

실험 결과를 반영해 기획안의 "LLM 확신도가 낮으면 일임" 구조를 아래처럼 바꾼다.

단계 하는 일 근거
0. 묻기 전에 명세, 결정 장부(DECIDED 노트), 코드에 답이 있으면 묻지 않는다. 상담 실행이 이미 이 일을 한다 상담 실행 26회 오류 0
1. 결정적 신호 먼저 경로 소유권(어느 역할이 그 파일을 소유하나), 운영 반영(배포, 운영 DB, 되돌리기 어려운 삭제)은 규칙으로 정한다. 운영 반영은 무조건 대표 승인 경로 소유권은 서버가 이미 안다. v1 LLM 오답의 상당수가 여기서 나왔다
2. LLM 라우터 owner와 확신도를 낸다. 소비자 요구는 소비자에게, 응답 모양은 제공자에게 같은 경계 규칙을 프롬프트에 넣는다 실제 질문 94%, 백엔드 20문항 95%
3. 확신이 낮을 때 대표에게 몰지 않고 1순위 후보에게 보내되, 받은 사람이 버튼 하나로 넘길 수 있게 한다 "확신 낮으면 PM" 캐스케이드는 정확도를 낮추고 대표 부담만 늘렸다
4. 기록하고 배운다 넘기기는 곧 정답 라벨이다. 재배정 기록으로 프롬프트 예시와 팀 표를 고친다. 답은 결정 장부에 남겨 같은 질문에 자동으로 답한다 버그 트리아지 연구: 재배정 한 번에 평균 50일(Jeong 외, FSE 2009)

7. 더 넣으면 좋을 아이디어

아이디어 효과 비용 판단
결정 장부 재사용: 같은 결정을 다시 묻지 않게 답을 검색해 자동 응답 대표 부담 감소가 가장 크다 낮음(노트는 이미 있다) 이번 학기
질문 묶기: 같은 사람에게 가는 질문을 한 번에 모아 보낸다 끼어들기 횟수 감소 낮음 이번 학기
추천을 받아들이고 진행, 사후 확인: 추천 수락률 78%를 근거로 낮은 위험 질문은 가정하고 진행한 뒤 확인만 받는다 대기 시간 제거 중간(위험도 판정 필요) 이번 학기, 실험 조건으로
넘기기 버튼과 재배정 로그 오배정 비용 측정, 학습 데이터 낮음 이번 학기
대기 시간 기준과 자동 상향: 일정 시간 답이 없으면 대표에게 멈춘 태스크 감소 낮음(만료 3일은 있다) 이번 학기
Jev 같은 System 1 결정 모델 연결 지연과 비용 감소 중간 기말 비교 실험 하나로만
질문 품질 검사: 선택지와 추천, 맥락이 빠진 질문은 돌려보낸다 답하는 사람의 시간 절약 낮음 여유가 있으면
역할 5개 이상으로 확장, 비판, ERD, 스케줄러 에이전트 불확실 높음 보류(교수님 피드백: 고생 대비 임팩트가 작다)

8. 기말까지의 평가 계획

질문 두 개

  • 할당이 맞게 되는가. 팀원 세 명이 질문 300개(실제 질문 + 보류 세트 + 실험 중 생긴 질문)에 블라인드로 owner를 붙이고 일치도(카파)를 낸다. 라우터별 첫 수신자 정확도, 대표 부담, 넘기기 횟수, 질문에서 답까지 걸린 시간을 잰다.
  • 공통 계약 위에서 병렬 개발이 되는가. 같은 과제를 네 조건으로 돌린다.
조건 설명
A Claude Code 한 세션, 한 사람
B Claude Code agent teams, FE와 BE 팀원, 한 사람
C NOMOS, 질문 중계 끔(에이전트는 가정하고 진행, 대조군)
D NOMOS, 질문 중계 켬 + owner 라우터 v2 + 최소 계약 먼저

지표는 네 개로 고정한다. 과제 성공(인수 테스트 통과), 끝날 때까지 걸린 시간, 토큰, 결정 때문에 생긴 재작업(계약 위반, 반려 횟수). 질문 관련 지표(정확도, 대표 부담, 대기 시간)는 C와 D 사이에서 본다.

일정(8주)

주 할 일
