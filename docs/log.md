**화면으로 직접 본 것은 없다.** 브라우저 자동화의 화면 캡처가 계속 시간 초과됐다(창이 가려진 것으로 보인다). 위 확인은 전부 DOM을 읽어서 한 것이다 → 사람이 한 번 눈으로 볼 것 (아래).

### 측정하면서 알게 된 것

- **룸에 들어오면 50줄만 받는다.** 500 · 2,000줄 "처음 그리기"는 진입으로는 만들 수 없어, "더 보기로 다 불러온 뒤 다른 화면에 갔다 돌아오기"로 정의했다
- **개발 모드 값은 예열 전후로 몇 배 달라진다.** 2,000줄 처음 그리기가 같은 세션에서 2.6초 → 0.7초로 떨어졌다. 그래서 예열 3회를 버리게 했고, 판단은 프로덕션 프로파일링 빌드 값으로 했다
- **창이 가려지면 측정 스크립트가 멈춘다.** Chrome이 가려진 탭의 타이머를 늦춘다. 처음에는 앱이 멈춘 줄 알았다
- 새 줄이 와도 화면의 줄 수가 그대로일 수 있다 — 불러온 페이지 수가 같으면 가장 오래된 줄이 다음 페이지로 밀려 화면에서 빠진다. 측정 스크립트가 "줄 수 증가"를 기다리다 멈춰서, 새 줄의 문장을 기다리게 고쳤다
- 프로덕션 기준값은 처음에 시나리오마다 새로 고침해서 쟀다가(2,000줄 처음 그리기 879ms), 변경 후와 같은 절차(`perfRoom.all`, 500 → 2,000줄 연속)로 다시 쟀다(1,315ms). 문서의 기준값은 다시 잰 값이다

### 사람이 확인할 것

- [ ] 실제 BE에 붙여 FE · BE 룸을 눈으로 본다 — 줄 모양, 질문 카드에 답하기, "생각 중" 표시, 새 줄이 올 때 맨 아래로 스크롤
- [ ] 질문 카드에 답을 쓰는 도중 새 줄이 와도 쓰던 답이 남아 있는지 (줄이 다시 그려지지 않으므로 남아야 한다)
- [ ] 더미의 줄 구성 비율이 실제 실행 피드와 비슷한지 (지금은 가정)
- [ ] 가상화 도입 여부, "새 줄이 올 때 모든 페이지를 다시 읽는 것"을 고칠지 (줄이 수정 · 삭제될 수 있는지 명세 확인 필요)

## 2026-11-23 — 활동 로그 가상화 (#109, `perf/activity-virtual`)

결과는 [perf-activity.md](./perf-activity.md), 결정은 [adr/0021](./adr/0021-활동-로그-가상화.md).

### 한 일 (순서대로)

1. 목 서버에 이벤트 경로(`/projects/:id/events`, 30건씩) · 3,000건 더미 · `/__perf/events/push`를 더했다. 활동 페이지를 `PerfProfiler`로 감싸고 `perf/collect.js`에 `perfActivity.run`(처음 그리기 · 새 이벤트 · 스크롤)을 더했다. 화면별 설정(`ROOM` · `ACTIVITY`)으로 나눠 룸 시나리오는 그대로 돈다
2. 보이는 Chrome 창에서 재다가 스크롤이 초당 1프레임으로 나와 멈췄다. 창이 가려져 `requestAnimationFrame`이 줄어든 것이었다 → 헤드리스 Chrome을 CDP로 모는 `perf/run-activity.mjs`를 만들어 전후를 모두 이것으로 쟀다
3. 기준 측정 (`baseline`)
4. 가상화 적용 → 동작 확인에서 "뒤로가기 하면 목록이 빈다"를 잡음 (스크롤 요소를 ref로 넘긴 탓) → state로 고침 → 측정 (`virtual`). 처음 그리기는 좋아졌는데 스크롤 프레임이 16.7 → 53.8ms로 나빠졌다
5. 날짜 포매터 재사용 → 측정 (`virtual-fmt`). 27.9ms
6. 줄 `memo` · `getItemKey` 고정 → 측정 (`virtual-memo`). 26.9ms — 차이 없음
7. 780건에서는 17.8ms로 정상이라 건수에 비례하는 비용을 찾았다 → `select`가 인라인 함수 → 훅 밖으로 → 측정 (`virtual-select`). 17.2ms
8. 몫을 가르려고 두 번 더 쟀다: 가상화 없이 포매터 · `select`만 (`novirtual-fixed`), 최종에서 `memo`만 뺀 것 (`virtual-plain`). `memo`는 빼면 스크롤 중 커밋 시간이 2.7배라 남겼다
