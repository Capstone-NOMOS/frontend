# ADR 0002. FSD 부분 도입 (4개 레이어)

- 상태: 확정 (이행 예정)
- 일자: 2026-09-22

## 맥락

현재 구조는 `components/{chat,dashboard,docs,inbox,activity,shell,ui}` + `lib/`다. 약 4,800줄 규모에서 당장 문제는 없지만, 곧 두 가지 큰 작업이 예정돼 있다 — API·WebSocket 경계 도입, 그리고 644줄짜리 `lib/store.tsx` 해체. 이때 "도메인 로직을 어디에 둘 것인가"를 반드시 결정해야 한다.

도메인은 명세 §3에 이미 확정돼 있어 경계가 또렷하다 — project / room / message / task / agent / document / policy / user.

## 결정

**`app` · `widgets` · `entities` · `shared` 4개 레이어만 도입한다.**

- FSD 원본의 `pages`는 만들지 않는다. Next App Router의 `src/app`과 역할이 겹친다
- **`features`는 지금 만들지 않는다.** 도입 기준은 아래에 명시한다
- 레이어마다 `ui/model/api/lib/config` 세그먼트를 기계적으로 만들지 않는다. 필요한 것만 만든다
- 목적은 폴더 정리가 아니라 스토어 해체 시 코드가 갈 자리를 미리 만드는 것이다

### 코드 검토에서 확인된 경계 충돌 2건

1. `shared/ui`의 `TaskBadge` `RoleBadge` `StatusDot`이 도메인 타입을 참조한다 → 각각 `entities/{task,user,agent}/ui`로 이동
2. `RoomView`가 `Cards` `Composer`를 참조한다 → 셋을 `widgets/room` 한 슬라이스로 묶는다

엔티티 간 참조 문제는 없다. 타입이 전부 ID 참조(`projectId`, `roomId`)이고 중첩 객체가 없다.

## `features` 도입 기준

아래 중 **하나라도** 발생하면 그때 만든다.

1. 같은 사용자 액션이 두 개 이상의 위젯에 등장할 때 (예: 승인·반려가 Room과 Inbox 양쪽에)
2. 정책 게이트가 액션에 붙을 때 — decider 값에 따라 버튼 표시·비활성·거부 문구가 갈리는 로직은 화면이 아니라 액션에 속한다
3. 한 액션이 여러 엔티티의 캐시를 동시에 무효화하고, 그 로직이 위젯마다 복제되기 시작할 때
4. 위젯 파일의 절반 이상이 액션 로직일 때

예상 슬라이스: `approve-spec`, `request-changes`, `answer-question`, `decide-report`, `connect-repo`, `change-level`, `join-project`. **미리 만들지 않는다.**

## 결과

- import는 `app → widgets → entities → shared` 단방향
- 같은 레이어끼리 import 금지. 슬라이스 바깥에서는 `index.ts`를 통해서만 접근
- 이행은 PR 4개로 쪼갠다: shared 이동 → entities 뼈대 → widgets 이동 → 경계 린트 적용
- 경계 린트(`eslint-plugin-boundaries` 등)를 CI에 넣는다. 린트가 없으면 폴더 이름만 바뀌고 규칙은 한 달 안에 무너진다

## 대안

전면 FSD 도입을 검토했으나, 예정된 두 작업과 겹치면 하나의 거대한 diff가 나와 리뷰가 불가능해진다. `features`까지 한 번에 만드는 것도 검토했으나 서버 연동 후 액션 모양이 바뀔 가능성이 커서 미뤘다.
