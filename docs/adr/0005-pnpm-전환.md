# ADR 0005. 패키지 매니저 pnpm 전환

- 상태: 확정 · 이행 완료 (#6)
- 일자: 2026-09-26

## 맥락

`create-next-app` 기본값인 npm으로 시작했고 `package-lock.json`을 쓰고 있었다. CI를 구축하면서 설치 단계를 고정해야 했고, 그 김에 패키지 매니저를 정했다.

이 레포는 의존성이 계속 늘어나는 구간에 있다. ADR 0002 이후 TanStack Query·Zustand·MSW·openapi-typescript 등이 한 번에 들어왔고, 실시간 라이브러리(adr/0004)와 Radix가 아직 대기 중이다.

## 결정

**pnpm으로 전환한다.**

1. **유령 의존성(phantom dependency)을 막는다.** npm은 평탄한 `node_modules`라 `package.json`에 선언하지 않은 패키지도 import된다. 의존성이 늘어나는 구간에서 이게 쌓이면 나중에 무엇을 지울 수 있는지 판단할 수 없게 된다
2. **버전을 `packageManager`로 고정한다.** 팀원과 CI가 같은 pnpm으로 설치한다
3. Vercel은 락파일로 패키지 매니저를 자동 감지하므로 **배포 설정 변경이 필요 없다**

## 결과

- `package-lock.json` 삭제, `pnpm-lock.yaml` 커밋. **락파일은 하나만 둔다**
- `packageManager: "pnpm@10.28.0"` — 버전 고정
- `engines`: `node >= 20.9` (adr/0001 결과 항목), `pnpm >= 10`
- CI는 `pnpm/action-setup` + `pnpm install --frozen-lockfile`
- `pnpm.onlyBuiltDependencies: ["msw", "unrs-resolver"]` — pnpm은 postinstall을 기본 차단한다. 승인하지 않으면 설치마다 경고가 뜬다. 이 목록에 패키지를 추가하는 것은 **스크립트 실행을 허용하는 것**이므로 패키지 추가와 같은 승인 대상으로 취급한다
- 명령은 `pnpm <script>`. `npm install`을 쓰면 `package-lock.json`이 되살아나므로 쓰지 말 것

## 재검토 조건

1. Vercel이나 CI에서 pnpm 특유의 심볼릭 링크 구조 때문에 빌드가 깨지고 `node-linker=hoisted`로도 해결되지 않을 때
2. 팀원 환경에 pnpm 10 이상을 설치할 수 없을 때
