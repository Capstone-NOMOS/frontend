# ADR 0001. Next.js 16 유지

- 상태: 확정
- 일자: 2026-09-22

## 맥락

레포는 `create-next-app`으로 Next.js 16.3.5 / React 19.2.8 위에 스캐폴드됐다. Next 16은 학습 데이터가 오래된 코딩 에이전트가 모를 수 있고, 실제로 `middleware.ts`처럼 15 기준의 코드를 만들어내기 쉽다. 이를 이유로 Next 15 다운그레이드를 검토했다.

다운그레이드 비용 자체는 낮았다. 목업에 16 전용 API가 사실상 없다 — `middleware`도 없고, `use cache`도 쓰지 않고, `next.config.ts`는 비어 있으며, `await params`는 15에서도 동작한다.

## 결정

**16을 유지한다.**

1. 16.x가 Active LTS이고 15.x는 Maintenance LTS다. 15로 내려가면 치명적 버그 수정과 보안 패치만 받는 브랜치로 들어간다
2. `proxy.ts`가 우리 요구에 더 맞다. 15의 middleware는 Edge 런타임이 기본이라 JWT 검증에 라이브러리 제약이 붙지만, 16의 `proxy.ts`는 Node 런타임으로 고정이라 제약이 없다
3. 에이전트 문제는 다운그레이드가 아니라 가드레일로 푼다. `AGENTS.md` 규칙 + `node_modules/next/dist/docs/` 참조 지시 + CI 검사
4. 버전을 낮춰 에이전트의 무지에 맞추는 것은 "모르면 문서를 읽거나 질문한다"는 이 프로젝트의 전제와 반대다

## 결과

- 가드는 `proxy.ts`에 작성한다
- `params` `searchParams` `cookies()` `headers()`는 전부 `await`한다
- 린트는 `eslint`를 직접 실행한다 (`next lint` 없음)
- 번들러는 Turbopack 기본. webpack 설정을 추가하지 않는다
- 팀 전원과 CI의 Node 버전을 20.9 이상으로 통일한다
- `AGENTS.md`의 `nextjs-agent-rules` 블록은 `next dev`가 생성·관리하므로 삭제하지 않고 커밋한다

## 재검토 조건

아래 중 하나가 발생하면 다시 논의한다.

1. 필요한 라이브러리가 16에서 동작하지 않을 때
2. Turbopack에서 빌드가 깨지고 `--webpack`으로도 해결되지 않을 때
3. 팀원 환경의 Node 버전을 20.9 이상으로 올릴 수 없을 때
