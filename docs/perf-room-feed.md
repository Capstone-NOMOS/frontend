# 룸 피드 성능 측정

역할 룸 피드(`widgets/room/RoleRoomView.tsx`)가 줄이 많을 때 얼마나 느린지 재고, 측정으로 확인된 병목만 고친 기록.
이슈 #104 · 브랜치 `perf/room-feed` · 작업 일지는 [log.md](./log.md).

## 한눈에

프로덕션 프로파일링 빌드, React 커밋 시간(렌더에 쓴 시간) 중앙값.

| 상황 | 줄 수 | 변경 전 | 변경 후 | |
| --- | --- | --- | --- | --- |
| "생각 중" 타이머 1틱 (실행 중 매초) | 500 | 138.4ms | 0.1ms | 고침 |
| | 2,000 | 619.7ms | 0.4ms | 고침 |
| 새 줄 1개 도착 | 500 | 167.3ms | 3.4ms | 고침 |
| | 2,000 | 668.0ms | 9.9ms | 고침 |
| 처음 그리기 (룸 재진입) | 500 | 246.9ms | 225.1ms | 그대로 — 고치지 않음 |
| | 2,000 | 1314.7ms | 1015.2ms | 그대로 — 고치지 않음 (오차 범위) |

- 에이전트가 실행 중일 때 2,000줄 피드는 **매초 약 0.6초** 동안 메인 스레드를 잡고 있었다. 지금은 "생각 중" 줄 하나만 다시 그린다
- 처음 그리기는 줄 수에 비례하는 DOM 생성 비용이다. 줄일 방법은 목록 가상화뿐이라 **승인 전에는 손대지 않았다** (아래 "바꾸지 않은 것")

## 측정 방법

### 환경

| | |
| --- | --- |
| 기기 | Intel Core i7-1165G7 (4코어 8스레드) · RAM 16GB · Windows 11 |
| 브라우저 | Chrome 157, CPU 스로틀 없음 |
| 런타임 | Node 22.14 · Next.js 16.3.5 (Turbopack) · React 19.2 |
| 프로덕션 값 | `next build --profile` + `next start` (React 프로파일링 빌드) |
| 개발 값 | `next dev` (StrictMode · 개발용 검사 포함 — 실제보다 느리다) |

### 더미 데이터

실제 BE 대신 API 계약 모양의 목 서버를 쓴다: `perf/mock-server.mjs` (`node:http`만 사용, 의존성 추가 없음, 제품 코드 아님).
룸 화면이 부르는 13개 GET과 화면용 웹소켓 `/api/stream`을 흉내 낸다. 값은 전부 지어낸 것이다 — 실제 팀 데이터·개인정보 없음.

시드 고정 난수로 만들어 매번 같은 피드가 나온다 (시각만 실행 시점 기준).

| 줄 종류 | 500줄 | 2,000줄 | 비율 |
| --- | --- | --- | --- |
| 도구 블록 (read · edit · write · run · search · other) | 252 | 1,001 | 50% |
| 시스템 줄 (PM · NOMOS 문장, 실행 시작/끝 포함) | 127 | 509 | 25% |
| 에이전트 말 (say, 짧은 문장 ~ 세 문장) | 92 | 352 | 18% |
| 질문 줄 (같은 `questionId` 두 줄씩 → 카드 하나로 묶임) | 24 (질문 12개) | 100 (질문 50개) | 5% |
| 사람 메시지 | 5 | 38 | 1~2% |

- 질문 상태는 사람이 답함 · 에이전트가 답함 · 만료를 2:1:1로 섞었다 (사람이 답한 질문은 답 말풍선이 하나 더 그려진다)
- 태스크는 25줄마다 하나, 전부 FE 역할
- 비율은 **가정**이다. 로컬 DB의 실제 피드(88줄)에는 에이전트가 실제로 돈 기록이 없어 도구·말 줄이 0이었다. "실행 중인 에이전트는 도구 줄을 가장 많이 남긴다"고 보고 정했다
- 화면에 그려지는 `<li>`는 500줄 → 495개, 2,000줄 → 1,977개다 (질문 줄이 묶이고 날짜 구분 줄이 더해진다)

### 무엇을 쟀나

`PerfProfiler`(`shared/ui`)가 룸 화면을 React `<Profiler>`로 감싼다. `NEXT_PUBLIC_PERF=1`로 띄웠을 때만 동작하고, 평소에는 children을 그대로 돌려준다.
기록하는 값은 `actualDuration` — 그 커밋에서 **렌더에 쓴 시간**이다. 레이아웃·페인트는 들어 있지 않다.

| 상황 | 재현 방법 (`perf/collect.js`) |
| --- | --- |
| 처음 그리기 | 피드 전체를 불러온 뒤 받은 편지함으로 갔다가 룸으로 돌아온다 → `mount` 커밋 |
| 새 줄 1개 도착 | 목 서버에 `POST /__perf/push` → 줄 추가 + `room` 신호 → `invalidateQueries` → 다시 읽기 → 가장 큰 `update` 커밋 |
| "생각 중" 1틱 | 끝나지 않은 실행이 있는 더미(`running=1`)에서 1초 타이머가 만든 커밋 하나 |

- 상황마다 **예열 3회를 버리고 5회**를 재서 중앙값과 최댓값을 적는다
- 다시 렌더된 컴포넌트와 이유는 커밋 직후 fiber 트리를 훑어 센다 (React DevTools와 같은 판정: `PerformedWork` 플래그 + 이번 렌더에서 시작. 이유는 이전 fiber와 props · state를 비교)
- **"처음 그리기"는 진입 그 자체가 아니다.** 룸에 처음 들어오면 API가 50줄만 준다(`limit=50`). 500 · 2,000줄은 "이전 줄 더 보기"를 9 · 39번 누른 뒤의 상태이고, 그 상태로 다른 화면에 갔다 돌아오면 캐시된 줄 전체가 한 번에 그려진다 — 이것을 쟀다
- 줄 계산(`belongsTo` · `toRows`)은 순수 함수라 Node에서 따로 쟀다 (`perf/bench-rows.mjs`, 200회)

### 다시 재는 법

```bash
node perf/mock-server.mjs                                   # http://localhost:3900

# 프로덕션 값
NEXT_PUBLIC_PERF=1 NEXT_PUBLIC_API_BASE_URL=http://localhost:3900/api pnpm exec next build --profile
pnpm exec next start -p 3001
# 개발 값
NEXT_PUBLIC_PERF=1 NEXT_PUBLIC_API_BASE_URL=http://localhost:3900/api pnpm dev

node --experimental-strip-types perf/bench-rows.mjs         # 줄 계산 시간
node perf/summarize.mjs                                     # perf/results 요약
```

브라우저에서 `http://localhost:3001/p/perf-project/rooms/frontend`를 열고 콘솔에:

```js
sessionStorage.setItem("nomos.session", JSON.stringify({ accessToken: "perf", expiresAt: Date.now() + 864e5 }));
location.reload();
// 다시 뜬 뒤
const s = document.createElement("script");
s.src = "http://localhost:3900/__perf/collect.js";
document.head.append(s);
await perfRoom.all("prod", "이름"); // 500 → 2,000줄, 약 5분. 결과는 perf/results/prod-<줄 수>-<이름>-{idle,running}.json
```

- `.env*`는 건드리지 않는다. 환경 변수는 명령 앞에 붙인다
- **탭을 보이는 채로 둔다.** 창이 가려지면 Chrome이 타이머를 늦춰 스크립트가 멈춘 것처럼 보인다 (커밋 시간 값 자체는 영향받지 않는다)

## 병목 판단

| 후보 | 측정 결과 | 판단 |
| --- | --- | --- |
| 새 신호마다 `toRows`가 전체 피드를 다시 계산하는가 | 다시 계산한다. 그런데 2,000줄에 0.03ms, 거르기까지 합쳐 0.09ms — 커밋 시간(668ms)의 0.01% | **병목 아님. 고치지 않음** |
| 1초 타이머가 피드 전체를 다시 렌더하는가 | 그렇다. 500줄 138ms · 2,000줄 620ms를 **매초** | **병목. 고침 (①)** |
| 행 컴포넌트가 불필요하게 다시 렌더되는가 | 그렇다. 새 줄 하나에 모든 줄이 다시 그려진다 (167 · 668ms) | **병목. 고침 (②)** |
| 2,000줄을 모두 DOM에 두는 비용이 지배적인가 | 처음 그리기에서는 그렇다 (1.0~1.3초). ① · ② 뒤에는 틱 · 새 줄에서 지배적이지 않다 | **가상화는 승인 대상 — 하지 않음** |

### 새 줄 하나에 모든 줄의 참조가 바뀌는 이유

피드는 최신 줄부터 50줄씩 페이지로 받는다(`useInfiniteQuery`). 새 줄이 하나 오면 모든 페이지를 다시 읽는데, 그때 **페이지 경계가 한 칸씩 밀린다** — 1페이지의 마지막 줄이 2페이지의 첫 줄이 된다.
react-query의 기본 구조 공유(`replaceEqualDeep`)는 배열을 **자리(인덱스)** 로 비교한다. 자리마다 다른 줄이 와 있으니 "전부 바뀌었다"고 보고 모든 줄을 새 객체로 만든다. 그래서 `memo`만 걸어서는 소용이 없다.

### ① "생각 중" 타이머를 작은 컴포넌트로 분리

- 전: `useThinking`이 `RoleRoomView` 안에서 `setInterval`로 `now` state를 매초 바꿨다 → 룸 전체가 매초 다시 렌더
- 후: `RoleRoomView`는 "실행 중이면 마지막 줄의 시각"만 계산해 `ThinkingRow`에 넘긴다. 타이머 state는 `ThinkingRow`가 갖는다 → 그 줄만 다시 렌더
- 다시 렌더된 것 (틱 1회): 전부(500줄 기준 약 1,900개 컴포넌트) → `ThinkingRow` · `LeftRow` · `AgentMark` 3개
- 6초 기준(`IDLE_MS`) · 문구 · `aria-live`는 그대로

### ② 새 줄이 와도 바뀌지 않은 줄은 다시 그리지 않게

둘이 함께 있어야 효과가 난다 (참조가 안정돼야 `memo`가 통한다).

- `useRoomFeed`에 `structuralSharing: keepMessagesById` — 같은 id의 줄은 이전 객체를 다시 쓴다. 내용이 바뀐 줄은 새 객체가 되므로 "줄은 바뀌지 않는다"는 가정을 하지 않는다. 바뀐 것이 없으면 이전 데이터 전체를 돌려준다(기본 동작과 같다)
- 줄 하나를 `memo`한 `FeedRow`로 뺐다. 이름 · 권한처럼 줄마다 계산하던 값은 부모가 문자열 · 불리언으로 넘긴다. 접힌 줄(`folded`)은 매번 새 배열이라 안의 줄로 비교한다
- 다시 렌더된 것 (새 줄 1개): 전부 → `RoleRoomView` + 새 줄 + 날짜 구분이 바뀌는 줄 등 20개 안쪽

## 바꾸지 않은 것과 이유

| 무엇 | 이유 |
| --- | --- |
| `toRows` · `belongsTo`에 `useMemo` 또는 증분 계산 | 2,000줄에 0.09ms. 재서 병목이 아니었다. 넣으면 의존성 관리만 늘어난다 |
| 목록 가상화 (`@tanstack/react-virtual`) | 처음 그리기(2,000줄 1.0~1.3초)를 줄일 유일한 방법이지만 **승인 대상**이다. 영향 범위는 아래 |
| 새 줄이 올 때 모든 페이지를 다시 읽는 것 | 2,000줄이면 신호 하나에 요청 40건(500줄은 10건)이 차례로 나간다. 목 서버(지연 0)에서도 신호 → 화면까지 0.5~1.3초. 고치려면 "첫 페이지만 다시 읽고 이어 붙이기"가 필요한데 줄 수정 · 삭제 가능 여부가 명세에 없다 → **질문 필요** |
| "이전 줄 더 보기"를 누를 때마다 전체가 다시 그려지는 것 | 같은 원인이라 ② 뒤로는 새로 온 50줄만 그릴 것으로 본다. 따로 재지는 않았다 |
| `PerfProfiler` | 남겼다. `NEXT_PUBLIC_PERF`가 없으면 children을 그대로 돌려준다 — 빌드 시점에 상수로 접힌다 |

### 가상화를 한다면 (승인 전 보고)

- 얻는 것: 처음 그리기가 줄 수와 무관해진다 (화면에 보이는 수십 줄만 그린다)
- 걸리는 것
  - 줄 높이가 제각각이다 (말풍선 · 도구 블록 · 질문 카드 · 접힌 줄). 높이를 재면서 그려야 하고, 재기 전에는 스크롤바가 흔들린다
  - 질문 카드는 입력 중인 답(로컬 state)을 갖는다. 화면 밖으로 나가 언마운트되면 **쓰던 답이 사라진다** → state를 위로 올려야 한다
  - 받은 편지함 · 토스트의 `#카드id`로 들어오는 스크롤(`scrollIntoView`)이 "아직 그려지지 않은 줄"에는 동작하지 않는다
  - "이전 줄 더 보기"로 위에 줄이 붙을 때 스크롤 위치 유지, 새 줄이 올 때 맨 아래 고정
  - 브라우저 찾기(Ctrl+F)가 화면 밖 줄을 못 찾는다
- 판단: 룸에 처음 들어오면 50줄만 받는다. 2,000줄 상태는 "더 보기"를 39번 누른 뒤다. 실사용에서 드문 상태에 위 위험을 지는 것은 지금은 과하다고 본다 — **팀 결정에 맡긴다**

## 한계

- 커밋 시간은 **렌더 시간**이다. 레이아웃 · 페인트 · 스크롤은 포함되지 않는다. 체감 시간은 이보다 길다
- 한 기기 · 한 브라우저에서 잰 값이다. 절대값보다 전후 비율을 볼 것
- 처음 그리기 2,000줄은 회차마다 흔들린다 (881~1,481ms). 기준과 변경 후의 차이(1,315 → 1,015)는 이 범위 안이라 개선으로 보지 않았다
- 더미의 줄 구성 비율은 가정이다. 질문 카드가 많은 피드는 줄당 비용이 더 크다
- 목 서버는 지연이 0이다. 실제 네트워크에서는 "신호 → 화면" 시간이 요청 수(페이지 수)만큼 더 길어진다
