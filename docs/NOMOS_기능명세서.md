# §0. 확정 사항

회의(2026-09-14)에서 결정된 내용입니다. 이 문서의 모든 기능은 아래를 전제로 합니다.

## 0-1. 허용 레벨 = 행동별 승인 정책표 ⭐

"레벨"은 자율성 정도가 아니라 **행동마다 누가 승인하는가**를 정한 표입니다. 프로젝트마다 L1~L4 중 하나를 고르면 이 표의 해당 열이 적용됩니다.

| # | action_key | 탐지 | L1 | L2 | L3 | L4 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `code:own_path` | diff 경로 ∈ 소유 레포 | AUTO | AUTO | AUTO | AUTO |
| 2 | `test:write` | diff `tests/**` | AUTO | AUTO | AUTO | AUTO |
| 3 | `human:ask` | MCP 호출 | 🔒 AUTO | 🔒 | 🔒 | 🔒 |
| 4 | `dispute:raise` | MCP 호출 | AUTO | AUTO | AUTO | AUTO |
| 5 | `contract:propose` | MCP 호출 | HUMAN | PM_REVIEW | PM_REVIEW | AUTO |
| 6 | `artifact:submit` | V1~V3 통과 후 | HUMAN | AUTO | AUTO | AUTO |
| 7 | `git:pr_open` | 브릿지가 gh CLI | PM_REVIEW | AUTO | AUTO | AUTO |
| 8 | `dep:add` | `package.json` / `requirements.txt` diff | HUMAN | PM_REVIEW | PM_REVIEW | AUTO |
| 9 | `file:delete` | diff 삭제 | HUMAN | PM_REVIEW | AUTO | AUTO |
| 10 | `contract:change` | `contracts/**` diff | HUMAN | HUMAN | PM_REVIEW | PM_REVIEW |
| 11 | `db:migration` | `migrations/**`, `*.sql` | HUMAN | HUMAN | HUMAN | PM_REVIEW |
| 12 | `infra:ci` | `.github/**`, `Dockerfile` | HUMAN | HUMAN | HUMAN | PM_REVIEW |
| 13 | `budget:exceed` | PM·에이전트 토큰 누적 | HUMAN | HUMAN | HUMAN | HUMAN |
| 14 | `git:merge_main` | GitHub PR (각 레포) | 🔒 HUMAN | 🔒 | 🔒 | 🔒 |
| 15 | `scope:violation` | diff 경로 ∉ 소유 레포 | 🔒 FORBIDDEN | 🔒 | 🔒 | 🔒 |
| 16 | `secret:touch` | `.env*`, `*.pem`, `*secret*` | 🔒 FORBIDDEN | 🔒 | 🔒 | 🔒 |
| 17 | `deploy` | 도구 미존재 | 🔒 FORBIDDEN | 🔒 | 🔒 | 🔒 |

**판정 주체 정의**

| 주체 | 동작 | 결정적? |
| --- | --- | --- |
| **AUTO** | 서버 코드가 판정 (스코프·테스트·커밋 존재) | ✅ |
| **PM_REVIEW** | PM이 **반려만** 할 수 있음. 통과는 AUTO 검증이 결정 | 반려는 LLM, 통과는 코드 |
| **HUMAN** | 담당 사람(대표 또는 해당 역할)의 승인 카드 | — |
| **FORBIDDEN** | 시도 자체를 거부, 이벤트 로그에 기록 | ✅ |
| 🔒 | 레벨과 무관하게 고정. 대표도 못 바꿈 | — |

**기본값:** L2. L1은 "온보딩 첫 주" 용도로 안내.

**탐지는 전부 결정적입니다.** diff 경로, MCP 호출 이름, 파일 패턴 — LLM 판단이 하나도 없습니다. 이 표가 곧 F-15(권한)와 F-16(검증)의 정책 원본입니다.

## 0-2. PM 에이전트 = NOMOS 내장

- PM은 **NOMOS 서버에서 NOMOS의 API 키로** 실행됩니다. 사용자는 키를 등록하지 않습니다.
- **비용은 NOMOS(우리)가 부담**합니다. 따라서:
    - 프로젝트별 **PM 토큰 예산** 필수 (`budget:exceed` 게이트가 우리 돈을 지킵니다)
    - **모델 등급 분리** — 명세 작성은 Sonnet급, 라우팅·요약은 Haiku급
- Room 1·2·3의 PM은 **같은 인스턴스**, 방별 대화 컨텍스트만 분리. 프로젝트 문서(F-13)는 공유.

## 0-3. 레포 구조 = 완전 분리

- FE 레포와 BE 레포가 **각각 독립**. 통합 브랜치 없음.
- `git:merge_main`은 **각 레포의 main**에 대한 PR.
- 크로스 레포 원자성(FE main 머지됐는데 BE PR 대기 중)은 **v1 범위 밖**. v1은 "두 레포 모두 DONE이어야 PM이 보고서를 쓴다"로만 처리.

## 0-4. 계약 협상 = v1 포함

- PM이 태스크 분배 **전에** API 계약 초안을 작성하고, 양쪽 Room에 **동일한 계약 텍스트**를 전달.
- 에이전트는 `contract:propose`로 역제안 가능 (레벨에 따라 PM_REVIEW 또는 AUTO).
- 계약 자동 검증(OpenAPI diff)은 v2. v1은 PM 프롬프트 + 문서 저장까지.

## 0-5. 나머지 (제안대로 확정)

| 항목 | 결정 |
| --- | --- |
| Room 접근 | 대표는 모든 Room 읽기. FE·BE는 자기 Room만. FE·BE 에이전트는 PM을 통해서만 소통 |
| 에이전트 → 사람 질의 | 태스크 `WAITING_HUMAN`. 4h 무응답 → PM이 대표에게 알림. 24h → 대표가 대신 답 가능 |
| 완료 판정 | V1 스코프 + V2 테스트 + V3 커밋 존재. 계약 대조는 v2 |
| 레포 연결 | URL + 로컬 경로만 등록. 서버는 코드를 안 봄 |
| confirm 방식 | Room 내 승인 카드 (승인 / 수정 요청). 수정 최대 3회 |
| 지원 CLI | v1은 Claude Code만 |
| 대표의 에이전트 | 없음. PM만. 대표가 개발을 겸하면 FE/BE 역할 추가 |
| 역할당 인원 | 1명. 2명 이상은 v2 |
| 회원가입 | 자체 계정 (GitHub OAuth 아님) |

# §1. 시스템 개요

## 1-1. 한 줄 정의

> 대표·FE·BE가 각자의 코딩 에이전트를 NOMOS에 등록하면, 서버 호스팅 PM 에이전트가 요구사항을 명세로 정리해 대표 승인을 받고, 양쪽 에이전트에 동시 분배하며, 에이전트가 모르는 결정은 담당 개발자에게 되돌려 묻고, 결과를 검증해 대표에게 보고하는 플랫폼.
> 

## 1-2. 구성요소

```
┌─────────────────────────────────────────────────────┐
│  NOMOS 서버 (호스팅)                                  │
│  ├ 웹 앱 (대시보드, Room, MCP 문서)                    │
│  ├ PM 에이전트 (API 키로 실행)                         │
│  ├ 상태 기계 (태스크·승인·질의)                         │
│  ├ MCP 문서 서버 (명세·결정·계약)                       │
│  └ 이벤트 로그                                        │
└──────────────┬──────────────────────────────────────┘
               │ WebSocket + MCP
    ┌──────────┼──────────┐
    ▼          ▼          ▼
 대표 브라우저  FE 노트북   BE 노트북
              ├ 브릿지     ├ 브릿지
              └ Claude    └ Claude
                Code        Code
```

## 1-3. 역할

| 역할 | 사람 | 에이전트 | 볼 수 있는 것 |
| --- | --- | --- | --- |
| **대표** | 프로젝트 소유자 | PM (서버) | 모든 Room (읽기), 대시보드, 승인 큐 |
| **FE** | 프론트 개발자 | FE 에이전트 (로컬) | Room 1, 자기 태스크, MCP 문서 |
| **BE** | 백엔드 개발자 | BE 에이전트 (로컬) | Room 2, 자기 태스크, MCP 문서 |

## 1-4. Room 구조

| Room | 멤버 | 용도 |
| --- | --- | --- |
| **Room 3 (대표)** | 대표 + PM | 요구사항 입력, 승인, 보고 수신 |
| **Room 1 (FE)** | FE + FE 에이전트 + PM | 태스크 전달, 질의응답, 진행 확인 |
| **Room 2 (BE)** | BE + BE 에이전트 + PM | 동일 |

**PM만 세 Room에 전부 있습니다.** FE 에이전트와 BE 에이전트는 서로 직접 대화하지 않습니다.

## F-01. 회원가입 · 신원 발급 `P0`

**설명:** 사용자가 계정을 만들고 고유 신원 키를 받는다.

**흐름:**

1. 웹에서 아이디·비밀번호·닉네임 입력
2. 서버가 **사용자 키페어** 생성 (Ed25519). 공개키 = 신원, 비밀키는 사용자 브릿지에 저장
3. 화면에 "다음: 에이전트 연결" 안내

**수용 기준:**

- WHEN 가입 완료 THEN 서버 DB에 사용자 + 공개키가 저장된다
- WHEN 같은 아이디로 재가입 THEN 거절된다

**확정:**

- 자체 계정 (GitHub OAuth 아님)
- 키는 사용자당 1개. 프로젝트마다 다른 키가 아님

**메모:** 가장 흔한 기능. **데모 단계에서는 하드코딩된 계정 3개로 대체 가능.** 나중에 만들어도 됨.

## F-03. 에이전트 연결 (브릿지) `P0` ⭐ 최우선 스파이크

**설명:** 사용자 노트북에서 브릿지를 설치하고, 로컬 Claude Code를 NOMOS 서버에 연결한다.

**흐름:**

```bash
$ npx nomos connect
  → 로그인 (브라우저 승인. 브라우저를 열 수 없으면 연결 키 → adr/0008)
  → 로컬 Claude Code 감지 (claude --version)
  → 없으면 설치 안내
  → NOMOS MCP 서버를 Claude Code 설정에 자동 등록
  → 서버와 WebSocket 연결
  → "✓ 연결됨. 프로젝트에 참여하면 에이전트가 활성화됩니다."
```

**브릿지가 하는 일:**

- 서버로부터 태스크를 **WebSocket으로 수신** (폴링 아님)
- 태스크를 받으면 `claude -p "<프롬프트>" --output-format stream-json` 으로 로컬 에이전트 기동
- 실행 로그를 서버로 스트리밍
- 에이전트가 MCP 도구를 호출하면 서버에 전달
- 완료 시 결과(변경 파일 목록, 커밋 해시)를 서버에 제출

**수용 기준:**

- WHEN 서버가 태스크를 보내면 THEN 5초 안에 브릿지가 에이전트를 기동한다
- WHEN 에이전트가 파일을 수정하면 THEN 서버 화면에 실시간으로 로그가 뜬다
- WHEN 브릿지가 끊기면 THEN 서버가 30초 안에 오프라인으로 표시한다
- WHEN 사용자가 프로젝트에 참여하기 전 THEN 에이전트는 어떤 태스크도 받지 않는다

**확정:**

- v1은 Claude Code만 지원
- 브릿지는 Node.js CLI (`npx`로 설치)

**⚠️ 이게 전체 프로젝트의 전제입니다.** `claude -p --output-format stream-json`이 안 되면 설계를 바꿔야 합니다. **1주차에 이것부터 확인하세요.**

## F-04. 프로젝트 생성 (채팅형 온보딩) `P0`

**설명:** 대표가 대화하듯 프로젝트를 만든다.

**흐름 (채팅 UI):**

```
NOMOS: 새 프로젝트를 만들어볼까요? 이름이 뭔가요?
대표:  Jazzify
NOMOS: 어떤 프로젝트인지 한 줄로 알려주세요.
대표:  재즈 음원 추천 웹앱
NOMOS: 에이전트 허용 레벨을 정해주세요.
       [L1 전부 확인] [L2 위험한 것만] [L3 경계만] [L4 결과만]
대표:  L2
NOMOS: 기술 스택이 정해져 있나요? (없으면 PM이 제안합니다)
대표:  Next.js + FastAPI
NOMOS: 프로젝트가 생성됐습니다.
       초대 링크: https://nomos.app/join/Jz7k...
       [FE 초대] [BE 초대]
```

**생성되는 것:**

- 프로젝트 레코드 (이름, 설명, 레벨, 스택, PM 예산)
- 정책표 (§0-1의 해당 레벨 열을 `policies` 테이블로 복사)
- Room 3 (대표 + PM)
- PM 에이전트 인스턴스 (NOMOS 키로)
- MCP 문서 페이지 (빈 상태: 헌법 / 명세 / 결정기록 / 계약)
- 초대 링크 2개 (FE용, BE용 — 역할이 링크에 박혀 있음)

**수용 기준:**

- WHEN 생성 완료 THEN 대표가 Room 3에서 PM과 즉시 대화할 수 있다 (키 등록 없음)
- WHEN 초대 링크 생성 THEN 링크에 역할(FE/BE)이 포함되어 있다
- WHEN 레벨을 고르면 THEN 정책표의 해당 열이 프로젝트에 적용된다
- WHEN 레벨을 안 고르면 THEN L2가 기본값

## F-05. 프로젝트 초대 · 역할 배정 `P0`

**설명:** 멤버가 초대 링크로 참여하면 역할이 자동 배정되고 Room이 열린다.

**흐름:**

1. FE가 `https://nomos.app/join/Jz7k...?role=FE` 클릭
2. 로그인 (없으면 가입)
3. "Jazzify 프로젝트에 FE로 참여합니다. [참여]"
4. 서버: `project_members` 에 (user, project, role=FE) 저장
5. **Room 1 자동 생성** (FE + FE 에이전트 + PM)
6. FE 브릿지에 "프로젝트 참여됨" 이벤트 → 에이전트 활성화
7. 대표 화면에 "FE 참여 완료" 표시

**수용 기준:**

- WHEN FE가 참여하면 THEN Room 1이 생기고, FE는 Room 1만 볼 수 있다
- WHEN 같은 링크를 두 번 쓰면 THEN 두 번째는 거절된다
- WHEN 역할이 이미 채워진 링크를 쓰면 THEN "이미 FE가 있습니다" 거절
- WHEN 서버 DB를 조회하면 THEN (FE=병국, FE에이전트=병국의 Claude Code, BE=영훈, ...) 이 전부 있다

**확정:**

- 역할당 1명. FE 2명은 v2
- 참여 즉시 Room 생성, 레포 연결은 별도 (F-06)

## F-06. 레포 연결 `P1`

**설명:** 각 개발자가 자기 담당 레포를 프로젝트에 등록한다.

**흐름:**

```
Room 1에서:
NOMOS: FE 레포 URL을 알려주세요.
FE:    https://github.com/Capstone-NOMOS/jazzify-web
NOMOS: 로컬 경로도 알려주세요. (브릿지가 이 경로에서 에이전트를 실행합니다)
FE:    ~/dev/jazzify-web
NOMOS: ✓ 연결됨. FE 에이전트는 이 레포 안에서만 작업합니다.
```

**서버에 저장되는 것:** 레포 URL, 로컬 경로, 소유자(FE), 스코프 패턴(`**` = 레포 전체)

**수용 기준:**

- WHEN FE 레포가 등록되면 THEN FE 에이전트의 스코프가 그 레포로 제한된다
- WHEN BE 에이전트가 FE 레포 경로를 수정하려 하면 THEN 브릿지가 거부한다 (F-15)

**확정:**

- 서버는 코드를 안 봄. URL과 경로만 앎
- 프로젝트당 레포 2개 고정, **완전 분리** (통합 브랜치 없음)
- 각 레포는 자기 main만 가짐. 크로스 레포 원자성은 v2

## F-07. Room 접근 제어 `P0`

**설명:** 각 사용자는 자기 Room만 본다.

**규칙:**

| 사용자 | Room 1 (FE) | Room 2 (BE) | Room 3 (대표) | 대시보드 |
| --- | --- | --- | --- | --- |
| 대표 | 읽기 | 읽기 | 읽기+쓰기 | 전체 |
| FE | 읽기+쓰기 | ❌ | ❌ | 자기 태스크만 |
| BE | ❌ | 읽기+쓰기 | ❌ | 자기 태스크만 |
| PM | 쓰기 | 쓰기 | 쓰기 | — |

**수용 기준:**

- WHEN FE가 Room 2 URL에 접근하면 THEN 403
- WHEN 대표가 Room 1을 열면 THEN 대화를 볼 수 있지만 입력창이 없다

**참조:** §0-5 Room 접근

## F-08. PM 에이전트 (서버 호스팅) `P0`

**설명:** 프로젝트마다 하나의 PM 에이전트가 서버에서 돈다.

**PM이 하는 일:**

1. 대표의 요구사항을 **기능 명세**로 정리 (F-09)
2. 명세를 **태스크로 분해** — FE 태스크, BE 태스크
3. **API 계약 초안** 작성 (§0-4)
4. 대표 승인 후 양쪽 Room에 **동시 전달** (F-10)
5. 에이전트 질의를 **담당 개발자에게 라우팅** (F-11)
6. 완료 수합 → **검증 요청** → 대표 보고 (F-12)

**PM이 하지 않는 일:**

- 코드 작성
- 완료 판정 (검증은 서버 코드가)
- 승인 (사람이)

**구현:**

- LLM: **NOMOS의 API 키** (Anthropic). 사용자 키 등록 없음
- 모델 등급: 명세 작성·계약 초안 = Sonnet급 / 라우팅·요약·PM_REVIEW = Haiku급
- 시스템 프롬프트: 역할 + Room 구조 + 정지 조건 (실험 7-B 프롬프트 기반)
- 상태: Room별 대화 컨텍스트 분리, 프로젝트 문서(F-13)는 공유
- **예산:** 프로젝트별 PM 토큰 상한. 초과 시 `budget:exceed` → HUMAN

**수용 기준:**

- WHEN 대표가 Room 3에 요구사항을 쓰면 THEN PM이 60초 안에 명세 초안을 낸다
- WHEN PM이 태스크를 전달하면 THEN Room 1과 Room 2에 각각 메시지가 생긴다
- WHEN PM이 에이전트를 부른 뒤 THEN 같은 태스크에 대해 다시 부르지 않는다 (정지 조건)
- WHEN PM 예산이 80%에 도달 THEN 대표에게 경고
- WHEN PM 예산 초과 THEN 새 명세·분배가 멈추고 대표 승인 대기
- WHEN PM_REVIEW가 필요한 행동이 오면 THEN PM은 반려 사유만 낼 수 있고, 통과는 AUTO 검증이 결정

## F-09. 요구사항 → 명세 → 대표 confirm `P0` ⭐

**설명:** 대표가 말하면 PM이 정리하고 대표가 승인한다.

**흐름:**

```
Room 3:
대표: 사용자가 좋아하는 재즈 곡을 저장하고 비슷한 곡을 추천받는 기능

PM:   기능 명세 초안입니다.

      F-01 곡 즐겨찾기
        AC1: WHEN 곡 상세에서 ♥ 클릭 THEN 즐겨찾기에 추가
        AC2: WHEN 이미 즐겨찾기된 곡 THEN ♥가 채워져 표시
        AC3: WHEN 즐겨찾기 해제 THEN 목록에서 제거

      F-02 유사곡 추천
        AC1: WHEN 즐겨찾기 3곡 이상 THEN 추천 탭 활성화
        AC2: ...

      API 계약 초안
        POST /api/favorites  { songId } → 201 { id, songId, createdAt }
        GET  /api/recommendations → 200 { songs: [...] }

      태스크 분해
        BE: T-01 즐겨찾기 API / T-02 추천 API
        FE: T-03 ♥ 버튼 / T-04 추천 탭

      결정이 필요한 것 ⚠️
        · 추천 알고리즘: 장르 기반? 협업 필터링? → BE에게 물어보겠습니다
        · 즐겨찾기 상한: 없음? 100곡? → 대표님 결정 필요

      ┌──────────────────────────┐
      │ [승인] [수정 요청]         │
      └──────────────────────────┘

대표: [승인]

PM:   승인됐습니다. 명세를 문서에 저장하고 태스크를 전달합니다.
```

**서버 동작 (승인 시):**

- 명세 → MCP 문서 서버에 저장 (F-13), 버전 v1, LOCKED
- 태스크 4개 생성, 상태 READY
- 계약 초안 → 문서 서버에 저장
- F-10 트리거

**수용 기준:**

- WHEN 대표가 승인하면 THEN 명세가 문서 서버에 v1으로 저장된다
- WHEN 대표가 수정 요청하면 THEN PM이 수정본을 내고 다시 승인 카드가 뜬다
- WHEN 승인 전 THEN 어떤 태스크도 에이전트에 전달되지 않는다
- WHEN 명세에 "결정이 필요한 것"이 있으면 THEN 승인 카드에 명시된다

**참조:** §0-4 계약 협상, §0-5 confirm 방식

## F-10. 태스크 동시 분배 `P0`

**설명:** 승인된 태스크를 FE·BE 에이전트에 동시에 보낸다.

**흐름:**

```
서버 → Room 1: [PM] T-03, T-04 전달 + 명세 링크 + 계약 초안
서버 → Room 2: [PM] T-01, T-02 전달 + 명세 링크 + 계약 초안
서버 → FE 브릿지: WebSocket push { task: T-03, ... }
서버 → BE 브릿지: WebSocket push { task: T-01, ... }
```

**에이전트에 주입되는 프롬프트:**

```
당신은 Jazzify 프로젝트의 FE 에이전트입니다.
작업: T-03 ♥ 버튼 구현
수용 기준: [AC1, AC2, AC3]
API 계약: [contracts/F-01.yaml 내용]
작업 범위: ~/dev/jazzify-web/** 만 수정 가능
모르는 결정이 있으면 ask_human 도구로 FE 개발자에게 물어보세요.
완료하면 submit_task 도구를 호출하세요.
```

**수용 기준:**

- WHEN 승인되면 THEN 1분 안에 두 Room에 태스크가 뜨고 두 브릿지가 에이전트를 기동한다
- WHEN 한쪽 브릿지가 오프라인이면 THEN 그 태스크는 QUEUED 상태로 대기하고, 대표 대시보드에 "BE 오프라인" 표시
- WHEN 태스크에 계약이 첨부되면 THEN 양쪽 프롬프트에 **동일한** 계약 텍스트가 들어간다

## F-11. 에이전트 → 사람 질의 `P1` ⭐ 핵심 차별점

**설명:** 에이전트가 명세에 없는 결정을 만나면 담당 개발자에게 묻고 기다린다.

**흐름:**

```
BE 에이전트 (T-02 작업 중):
  → ask_human(
      question: "추천 알고리즘을 정해야 합니다.
                 (a) 장르 태그 기반 단순 매칭
                 (b) 협업 필터링 — 데이터가 더 필요
                 어느 쪽으로 갈까요?",
      options: ["a", "b"],
      context: "현재 사용자 데이터가 없어서 (b)는 콜드스타트 문제가 있습니다"
    )

서버:
  → T-02 상태: IN_PROGRESS → WAITING_HUMAN
  → Room 2에 질문 카드 표시
  → BE에게 알림 (웹 + 이메일?)
  → 타이머 시작

Room 2:
  ┌─────────────────────────────────────┐
  │ 🙋 BE 에이전트가 결정을 기다립니다      │
  │ 추천 알고리즘을 정해야 합니다.          │
  │  (a) 장르 태그 기반                   │
  │  (b) 협업 필터링                      │
  │ 맥락: 사용자 데이터가 없어 (b)는 ...   │
  │        [a] [b] [직접 입력]            │
  └─────────────────────────────────────┘

BE: [a]

서버:
  → 결정을 MCP 문서 서버의 결정기록(ADR)에 저장
     "ADR-003: 추천 알고리즘은 장르 태그 기반. 결정자: 영훈. 사유: 콜드스타트"
  → T-02 상태: WAITING_HUMAN → IN_PROGRESS
  → BE 브릿지에 재개 push { answer: "a", adr: "ADR-003" }
```

**타임아웃:**

- 4시간 무응답 → PM이 Room 3에 알림 "BE의 결정 대기 중 (4h)"
- 24시간 → 대표가 대신 답할 수 있게 카드 표시

**수용 기준:**

- WHEN 에이전트가 ask_human 호출 THEN 태스크가 WAITING_HUMAN이 되고 에이전트 프로세스는 종료된다 (토큰 소모 0)
- WHEN 사람이 답하면 THEN 30초 안에 에이전트가 답과 함께 재기동된다
- WHEN 답이 저장되면 THEN ADR에 (질문, 답, 결정자, 시각)이 남는다
- WHEN 같은 질문이 다시 나오면 THEN 에이전트가 ADR을 먼저 조회한다 (F-13)

**참조:** §0-5 질의 타임아웃

**이게 왜 핵심인가:** 앞서 논의한 "전문성" 축입니다. 에이전트가 지어내지 않고 물어보게 만드는 것. 그리고 그 답이 **문서로 남아서** 다음 에이전트가 다시 안 물어봅니다.

## F-13. MCP 문서 서버 `P1` ⭐

**설명:** 프로젝트의 확정된 사실을 저장하고, 에이전트가 MCP로 조회한다.

**문서 4종:**

| 문서 | 내용 | 쓰기 권한 |
| --- | --- | --- |
| **헌법** | 스택, 컨벤션, 금지사항 | 대표만 |
| **명세** | 기능별 수용 기준 (F-09에서 생성) | PM (대표 승인 후) |
| **계약** | API 스키마 (OpenAPI) | PM (대표 승인 후) |
| **결정기록 (ADR)** | 질의응답 결과 (F-11에서 생성) | 서버 자동 (추가만) |

**MCP 도구:**

| 도구 | 설명 |
| --- | --- |
| `get_spec(feature_id)` | 기능 명세 조회 |
| `get_contract(feature_id)` | API 계약 조회 |
| `search_decisions(query)` | 결정기록 검색 |
| `get_constitution()` | 헌법 조회 |
| `ask_human(question, options, context)` | F-11 |
| `submit_task(task_id, commit)` | F-12 |
| `report_blocker(task_id, reason)` | 막힘 신고 |

**웹 페이지:** 프로젝트 메인에서 4종 문서를 사람이 읽을 수 있음. 버전 이력 표시.

**수용 기준:**

- WHEN 에이전트가 get_spec 호출 THEN 해당 기능의 명세만 반환 (전문 아님)
- WHEN 명세가 v2로 바뀌면 THEN v1 이력이 남고, 참조하던 태스크에 알림
- WHEN 사람이 웹에서 문서를 열면 THEN 마크다운으로 렌더링

**확정:** 문서는 서버 DB에 저장. 벡터 검색은 v2.

## F-15. 권한 · 정책 게이트 `P1` ⭐ 핵심 차별점

**설명:** 에이전트의 모든 행동을 §0-1 정책표로 판정한다. 스코프 밖 수정은 항상 FORBIDDEN.

**동작:**

```
브릿지 또는 서버가 행동 감지 (diff 경로, MCP 호출명, 파일 패턴)
  → action_key 결정
  → policies 테이블에서 (project, action_key) → decider 조회
  → AUTO: 즉시 진행
  → PM_REVIEW: PM에게 반려 기회 → 반려 없으면 AUTO 검증
  → HUMAN: 담당자 Room에 승인 카드, 태스크 WAITING_HUMAN
  → FORBIDDEN: 거부 + 이벤트 로그
```

**구현 (브릿지):**

- Claude Code의 PreToolUse 훅으로 파일 쓰기 도구 가로채기
- 경로가 스코프 밖이면 거부 + 사유 반환
- 훅이 안 되면: sparse-checkout으로 담당 폴더만 체크아웃

**구현 (서버):**

- submit_task 시 diff의 모든 경로를 스코프와 대조
- 위반 시 반려

**수용 기준:**

- WHEN FE 에이전트가 BE 레포 경로를 쓰려 하면 THEN 거부되고 "이 경로는 BE 소유입니다" 메시지
- WHEN 우회해서 수정한 뒤 제출하면 THEN 서버가 diff에서 잡아 반려
- WHEN 거부되면 THEN 이벤트 로그에 (누가, 어디를, 언제) 남는다

**메모:** 실험 1에서 Buzz가 못 막은 것. **발표 데모 10초 장면.**

## F-16. 제출 검증 `P1`

**설명:** 에이전트가 "완료"를 주장하면 서버가 판정한다.

**v1 검증 항목:**

1. **스코프** — diff 경로가 전부 스코프 안인가 (F-15)
2. **테스트** — 레포에 테스트가 있으면 실행, exit code 확인
3. **커밋 존재** — 제출한 커밋 해시가 실제로 있는가

**v2:**
4. 계약 대조 — OpenAPI 스키마 비교

**수용 기준:**

- WHEN 검증 실패 THEN 태스크가 DONE이 되지 않고 사유가 에이전트에 전달된다
- WHEN 3회 연속 실패 THEN PM에게 알림 + 태스크 ESCALATED

**참조:** §0-5 완료 판정. 테스트 실행은 **브릿지(로컬)에서** 하고 결과만 서버로. 서버는 코드를 안 봄.

**정책표와의 관계:** V1~V3 통과 후 `artifact:submit` 행동이 발생하고, 그때 레벨에 따라 HUMAN 또는 AUTO로 DONE 처리된다.

## F-17. 이벤트 로그 · 비용 계측 `P1`

**설명:** 모든 일을 기록하고 비용을 사람별로 센다.

**이벤트 (예시):**

```
task.created, task.assigned, task.started, task.waiting_human,
task.resumed, task.submitted, task.verified, task.done,
approval.requested, approval.granted, approval.rejected,
scope.violation, agent.online, agent.offline,
llm.call { agent, task, tokens_in, tokens_out, cost }
```

**비용 귀속:**

- FE 에이전트 호출 → FE 계정 (브릿지가 토큰 수를 보고)
- BE 에이전트 → BE 계정
- **PM → NOMOS 계정, 프로젝트별 집계** (우리 비용이므로 프로젝트별 상한 필수)

**수용 기준:**

- WHEN 어떤 상태 변화가 일어나면 THEN 이벤트가 append된다 (삭제·수정 불가)
- WHEN 대시보드를 보면 THEN 태스크별·사람별 비용이 보인다
- WHEN 프로젝트 예산을 넘으면 THEN 새 태스크 분배가 멈추고 대표에게 알림

**메모:** **1일차부터 만드세요.** 나중에 평가 지표가 전부 여기서 나옵니다.

## 원칙

## 순서

### 1단계 — 스파이크 (1주차) ⚠️ 여기서 막히면 설계 변경

```
F-03 브릿지 최소판
  □ claude -p "hello" --output-format stream-json 파싱
  □ 서버 → 브릿지 WebSocket으로 프롬프트 전달
  □ 브릿지 → 서버 로그 스트리밍
  □ MCP 서버 하나 띄우고 Claude Code가 도구 호출하는지 확인
```

**게이트:** 서버가 태스크 주고 diff 받기. 이게 되면 전체가 성립.
