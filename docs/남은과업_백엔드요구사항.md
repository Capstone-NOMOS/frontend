## 2. 백엔드 요구사항 (프론트가 필요로 하는 순서)

> 우선순위: **P0** = 데모 불가 / **P1** = 핵심 차별점 / **P2** = 있으면 좋음
> 모든 응답은 camelCase JSON, 시간은 ISO-8601, ID는 문자열. 타입 이름은 `src/lib/types.ts`와 1:1.

### 2-1. 인증 · 신원 `P0` (F-01, F-02)
| 메서드 | 경로 | 요청 → 응답 | 비고 |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/signup` | `{username, password, nickname}` → `201 {user: User}` | 서버가 Ed25519 키페어 생성, `pubkey` 반환. 중복 → `409` |
| POST | `/api/v1/auth/login` | `{username, password}` → `200 {token, expiresAt, user}` | 사람 토큰 1h, refresh 없음. 쿠키 없이 body로 받는다 (→ adr/0007) |
| GET | `/api/v1/me` | → `{user, agent?: Agent}` | 셸 부팅 시 1회 |
| POST | `/api/v1/auth/logout` | → `204` | 쿠키 방식이면 필요 |

### 2-2. 에이전트 · 브릿지 `P0` (F-03)
| 메서드 | 경로 | 요청 → 응답 | 비고 |
| --- | --- | --- | --- |
| GET | `/api/v1/agents/me` | → `Agent {id, harness:"claude-code", status, lastSeen, connected}` | `/connect` 화면 폴링 또는 WS |
| WS | `agent.status` 이벤트 | `{agentId, status: online\|working\|offline, lastSeen}` | 30초 무응답 → offline (서버가 판정) |
| POST | `/api/v1/agents/connect-token` | → `{token}` | `npx nomos connect` 가 쓸 일회용 토큰 (선택) |

### 2-3. 프로젝트 · 초대 · 멤버 `P0` (F-04, F-05)
| 메서드 | 경로 | 요청 → 응답 | 비고 |
| --- | --- | --- | --- |
| GET | `/api/v1/projects` | → `{projects: (Project & {myRole})[]}` | 목록 화면 |
| POST | `/api/v1/projects` | `{name, description, level, stack?}` → `201 {project, room, inviteTokens:{FE,BE}}` | 정책표 복사, Room 3, PM 인스턴스, 빈 문서 4종 생성. 레벨 미지정 → L2 |
| GET | `/api/v1/projects/{id}` | → `{project, members:[{user, role, joinedAt}], agents:[Agent], repos:[Repo], rooms:[Room]}` | 대시보드·셸 1회 로드 |
| GET | `/api/v1/invites/{token}` | → `{project, role, taken: boolean}` | 참여 페이지 미리보기 |

| GET | `/api/v1/projects/{id}/repos` | → `{repos}` | — |

### 2-5. Room · 메시지 `P0` (F-07, F-08)
| 메서드 | 경로 | 요청 → 응답 | 비고 |
| --- | --- | --- | --- |
| GET | `/api/v1/rooms/{id}/messages?before=&limit=50` | → `{messages: Message[], hasMore}` | 접근 불가 → `403`. **`Message.card`는 `types.ts`의 `Card` 유니온 그대로** |
| POST | `/api/v1/rooms/{id}/messages` | `{text}` → `201 {message}` | 읽기 전용(대표가 Room 1·2) → `403`. Room 3에서는 PM 파이프라인 트리거 |
| WS | `message.created` | `{roomId, message}` | 카드 포함. PM 응답·에이전트 로그·시스템 카드 전부 이 이벤트 |
| WS | `message.updated` | `{roomId, messageId, card}` | 카드 상태 변화(승인됨, 답변됨, 로그 live→done) |
| WS | `pm.typing` | `{roomId, on}` | 선택. 있으면 UI가 "PM이 명세를 정리하는 중" 표시 |

**카드 종류(프론트가 렌더링하는 계약):** `spec` · `dispatch` · `log` · `question` · `verification` · `report` · `policy` · `repo` · `notice` — 필드는 `src/lib/types.ts` `Card` 참고. 새 카드 종류를 추가할 때는 프론트에 먼저 알려주세요.

### 2-6. 명세 · 승인 `P0` (F-09)

## 3. 연결 순서 제안 (프론트 관점 스프린트)

1. **인증 + 프로젝트 조회** (2-1, 2-3 GET) → 셸·대시보드가 실데이터로 뜸
2. **Room 메시지 + WS `message.created`** (2-5) → Room 3에서 PM과 실제 대화
3. **승인 파이프라인** (2-6, 2-7) → 명세 승인 → 태스크 카드 도착 → 로그 스트리밍
4. **질의 응답 + ADR** (2-8, 2-10) → 발표 2:30 장면
5. **정책 거부 + 이벤트/비용** (2-11, 2-12) → 발표 4:00 · 4:40 장면
6. 보고서 · 설정 · 검색

## 4. 백엔드에 묻는 것 (미결)

- 승인/질의 카드의 식별자: `messageId`로 결정 API를 호출해도 되나, 아니면 `approvalId`/`questionId`를 카드에 넣어줄 것인가? (프론트는 후자를 선호)

- 초대 링크 도메인(`nomos.app/join/...`)과 만료 정책(1회용? 시간 제한?)

- PM 타이핑 인디케이터(`pm.typing`)를 보낼 수 있는지 — 없으면 프론트가 "요청 중" 상태로 대체
